# Dungeon World Digital Control Panel Design

## Overview

This document outlines the requirements for a comprehensive digital control panel for Dungeon World tabletop roleplaying game, designed to streamline gameplay and enhance the player experience.

## Product Vision

A sophisticated, user-friendly digital interface that transforms the traditional Dungeon World character sheet into an interactive, dynamic control panel that supports both solo and group play.

## Overall Layout Framework

Design the interface as a single-screen dashboard with a clear, modular layout for quick reference and minimal navigation.

## Core Features

### Character Stats & Health Panel

- Display character attributes and status
- Show HP, armor, damage die, and experience
- Track load and encumbrance
- Provide quick roll options

### Equipment Panel

- List equipped items with tags and stats
- Support equip/unequip functionality
- Show item details and custom moves
- Enable rapid actions and editing

### Inventory Panel

- Manage carried items and weight calculation
- Support add/remove/edit items
- Track coin and currency
- Provide organizational aids

### Moves Panel

- Organize basic, class, and custom moves
- Support roll automation and move descriptions
- Enable custom move creation
- Include spell management for casters

### Session Tools Panel

- Provide dice roller and note keeper
- Support hold/charge/counter trackers
- Include session timers and bookmarks
- Maintain roll and event log

### Lore / Journal Panel

- Record session logs and journal entries
- Store world lore and reference information
- Track bonds and alignment
- Support searchable reference

## Technical Requirements

### Performance

- Fast panel switching and data synchronization
- Responsive layout for different screen sizes
- Efficient drag-and-drop functionality
- Quick modal overlays and tooltips

### Security

- Local data storage and privacy
- Export/import functionality
- Backup and recovery options
- User preference management

### Integration

- Keyboard shortcuts and accessibility
- Context menus and right-click actions
- Hover behaviors and tooltips
- Panel state preservation

## Success Metrics

- Reduced time spent on character sheet management
- Improved gameplay flow and immersion
- Enhanced solo play experience
- Positive user feedback and adoption

- Phase 3: Polish and optimization (Q3) A two-column or three-zone approach works well for desktop: one section remains persistent for vital stats, while other sections display context-specific information[1]. For example, a left sidebar can hold always-visible character vitals (HP, stats, etc.) and shortcut actions, and a main area to the right can switch between panels like Moves, Inventory, or Notes[2]. A right-hand drawer or pop-up panel can be used for auxiliary tools (dice roller, quick notes) that slide in when needed and hide otherwise. This ensures the player isn’t constantly changing screens – most actions and info are accessible at a glance or a single click, reflecting Dungeon World’s fast-paced, fiction-first gameplay.
  The interface should be mostly static with tabs or buttons to swap the central panel content. For instance, top navigation tabs (or icons) might toggle the main area between Character, Moves, Inventory, Journal, etc. Modals and overlays are used sparingly, mainly for drilled-down details (like viewing a detailed item card or move description) without losing the main view. The layout should also be responsive – on a smaller window, the sidebars can collapse into icon toolbars or accordion sections, but on desktop, they can all be visible for maximum information density. This way the design remains desktop-optimized but can gracefully adjust if resized.
  Key layout zones might include:
  • Header Bar (optional): Could display character name, class, level, and maybe quick-access icons (dice roller, settings).
  • Left Sidebar (Fixed HUD): Character’s core stats and status – always on screen for quick reference (like a HUD in a video game)[1]. This might also contain quick action buttons (e.g. “Roll Damage” or common moves).
  • Central Play Space: The primary panel area, showing one of the core panels (Moves, Equipment, Inventory, etc.) in detail. This area is scrollable if needed but should prioritize the most relevant info at the top.
  • Right Side Drawer/Overlay: A collapsible panel for Session Tools (dice roller, notes, trackers). It can be a toggleable drawer that overlaps the right side of the screen when opened, or a floating toolbox window. This keeps tools one click away but offscreen when not in use, preserving clarity.
  • Pop-up Modals: Used for content that benefits from focus without navigating away – e.g., clicking an item or move could open a small modal with the full description or options. Modal overlays should be used for editing forms (like adding a new item or move) or displaying large text (like a custom move explanation), then closed to return to the main view. Keep modals lightweight and easy to dismiss (click X or outside).
  Overall, the framework emphasizes usability and clarity. Panels are organized logically, matching a typical character sheet’s groupings, so players intuitively know where to find things. The single-screen design means during play, a user can see their HP, stats, and a move they’re triggering all at once without flipping pages. The layout takes inspiration from modern digital character sheets that avoid multi-step menus: for instance, a concept design for D&D Beyond kept a static column for at-a-glance stats and a swappable main section for actions/inventory, to minimize constant menu flipping[1][2]. In our Dungeon World panel, this translates to keeping crucial info (health, XP, etc.) always visible, while the rest is one click away.
  Core Panels to Include
  The control panel consists of several core panels, each focused on a gameplay-critical area. Each panel’s content and layout are described below:
  Character Stats & Health Panel
  This panel (likely in a left sidebar or top section) displays all essential character attributes and status. It functions as the character’s summary at a glance. Key elements to include:
  • Character Info: Character name, Class, Level, and Alignment. These can appear at the top for context. The level and XP are especially important in Dungeon World; show current level and current XP prominently, e.g. “Level 3, XP 6/10”. Level and XP might also be in the header bar for quick reference.
  • Core Stats and Modifiers: List the six attributes (STR, DEX, CON, INT, WIS, CHA) along with their current scores and modifiers. The modifier should auto-calc from the score (e.g. 15–16 gives +1, etc.), or allow direct entry of mod if that’s simpler. Present both score and mod clearly (e.g. “STR 15 (+1)”). Debility checkboxes next to each stat let the player mark if a debility applies (e.g. Weak for STR, Shaky for DEX, etc.), automatically adjusting the modifier by -1[3]. For example, checking “Weak” could gray out the STR label and reduce the mod by 1. Tooltips on these debility labels can remind what each means (“Weak: -1 STR modifier”).
  • Health (HP): Current and max HP, displayed as “HP: 18/25” or with a visual bar. This should be very prominent (maybe with a heart icon) since it’s critical in play. Include quick buttons to adjust HP (like +/- buttons to add or subtract damage, or clickable damage values). The HP display might change color or flash when low or at 0. If HP hits 0 or below, the system could prompt the Last Breath move automatically (since reaching 0 HP triggers that move in Dungeon World).
  • Armor: The character’s Armor value (damage reduction) is shown here. It can be auto-calculated from equipped armor pieces[4][5], but also allow manual override/edit in case of temporary effects. This is usually a small number (e.g. Armor 1 or 2), but important to see at a glance.
  • Damage Die: Dungeon World characters have a class damage die (e.g. d6, d8). Display the damage die (perhaps as an icon or “Damage: d8”). A button to roll this die is useful for when the player needs to roll damage (for example, clicking “Damage” could roll the set die and output the result[6]).
  • Experience (XP): Current XP count and the next level threshold. Dungeon World uses the formula “Level+7” as the XP needed to level up[7], so if the character is level 3, it would show “XP: 6/10” (since 3+7=10 XP needed). This panel can visualize XP progress (like a small bar or just fraction text). When XP is increased, if it meets or exceeds the threshold, highlight the XP or level (e.g. glow or an icon) to indicate the Level Up move is available. (We’ll detail the level-up prompt in interactions).
  • Load (Encumbrance): Display current carried weight vs. Load capacity. For example, “Load: 5/9”. Load capacity in DW is typically base Load (from class) + STR modifier[8], so the system should compute that. Show the number clearly and possibly an icon of a backpack. If the current weight is within normal range (<= Load), display normally; if it exceeds Load (up to Load+2), maybe color it yellow or add “Encumbered” label (since the character moves at -1 ongoing when carrying <= Load+2)[9]. If it exceeds Load+2 (overburdened), color it red or “Overburdened” (cannot move effectively) for quick warning[9]. This real-time feedback helps the player manage inventory before penalties hit.
  • Other Status: If relevant, include fields for Bonds and Alignment here or nearby. For example, list current bond statements (or a count of bonds) and alignment goal. However, these might also reside in a Journal panel. At minimum, having alignment visible (to remember the XP trigger) is handy; it could be a small text like “Alignment: Chaotic (eschew a convention of the civilized world)”. Bonds could be a number or a button that opens the detailed Bonds list (possibly in the Journal or a popup). DungeonPaper emphasizes tracking bonds, flags, alignment, and session experience easily[10], so our design should allow quick access to these role-playing hooks, even if not always on screen.
  Quick Roll Options: To speed up gameplay, the Stats panel offers one-click rolls for common actions: - Clicking on a Stat Modifier should trigger a 2d6 + mod roll for that stat[3]. For instance, clicking the “+1” next to STR would roll 2d6+1 (useful for hack & slash or any STR-based move). This acts as a generic “roll +Stat” shortcut. The result can display in a small log area or as an overlay (with the total and maybe a brief outcome message like “Roll+STR total 8 (partial success)” to remind the success tier). - A “Roll Damage” button (next to the Damage die) lets the player roll their class damage quickly (especially useful if a move calls for direct damage roll outside of the standard hack & slash, or for GM moves in solo play). The damage roll result could simply pop up on screen or in a log. - Healing or Other Rolls: If the character has a healing potion or similar, those are handled via item or move, but general-purpose dice can be rolled from the Session Tools dice roller. The focus here is stat and damage rolls since those are frequent and need to be fast. - Forward/Ongoing Modifiers: Dungeon World often uses +1 or -1 forward/ongoing modifiers. A small toggle or menu for global roll modifiers can be included (similar to Roll20’s sheet which offers +1/-1 forward toggles)[11]. For example, a drop-down or set of radio buttons labeled “No modifier / +1 Forward / -1 Forward / Custom…”. If set, the next applicable roll would include that. This could live at the top of the Stats panel or near the dice roller. It’s a nice-to-have for advanced play, but if complexity is undesired, the player can always mentally adjust or use the dice roller to add modifiers.
  Overall, the Stats & Health panel acts as a HUD for the character’s state. It must remain readable at a glance, using icons or labels for clarity (heart for HP, shield for Armor, pack for Load, star for XP, etc., with tooltips on hover). It’s always visible so the player can monitor their status while engaging with other panels. The design should use clear typography and possibly slight color accents for different stat types, but avoid clutter. Short tooltips can provide any needed rule reminders (e.g. hover over “Load” could show “Encumbered at > Load (–1 ongoing), Overburdened at > Load+2[9]”). Fast access to all these bits ensures the player can make decisions quickly without digging through a character sheet.
  Equipment Panel
  The Equipment panel lists the items the character currently has equipped or readily accessible (worn, wielded, etc.). This is essentially the “what I have in hand/on body” view, distinct from the full inventory. Key features of this panel:
  • Equipped Items List: Show each equipped item as a distinct entry, possibly with an icon or a category label (e.g. Weapon, Armor, Other Gear). For example:
  • Weapon: Sharp Sword – tags: close, 1 weight, +1 damage.
  • Armor: Chainmail – tags: 2 armor, worn, 3 weight.
  • Ring: Ring of Smooshed Chronologies – tags: 0 weight, magical (has custom move).
  Each entry should display the item’s name and essential tags or stats at a glance (Dungeon World items have descriptive tags like “close, 1 weight, messy” etc. which describe their effects). Include those tags in a smaller font under the name or alongside it[12]. This gives immediate info like how heavy or dangerous an item is without needing to click it. - Quick Info and Indicators: Important properties like an item’s weight or uses remaining should be visible. For example, if a healing potion is equipped with 2 uses left (tagged “2 uses”), show “Healing Potion (2/3 uses)”. If an item grants a bonus (like a weapon that adds +1 damage), that could be indicated (maybe “+1 damage” in the tags or a small icon). Items that are currently affecting character stats (e.g., armor providing Armor points, or a weapon modifying damage die) could be highlighted. The system may even dynamically reflect this: for instance, when an armor piece is equipped, the Armor stat in the Stats panel already updates[5], and when a weapon is equipped that adds to damage, the Damage roll is updated[5]. This dynamic link should be clear to the player (perhaps a brief animation or icon change when equipping something to show stats changed). - Item Interaction (Equip/Unequip): In a single-player context, equipped vs carried is mostly organizational, but an “Unequip” or “Stow” button next to each item will move it to the general inventory. Conversely, the Inventory panel will have an “Equip” action to bring items here. Drag-and-drop can provide a tactile way to equip items – for example, drag a sword from Inventory into the Equipment list to equip it, or drag it out (or to a trash icon) to unequip. This direct manipulation speeds up inventory management, though buttons are fine as well for accessibility. Equipping or unequipping should automatically update related stats (Armor, damage, total weight, etc.) and could play a brief sound or visual confirmation in the UI. - Item Details & Custom Moves: Many items in Dungeon World are simple, but some (especially magical or custom items) have special moves or effects. The UI should allow viewing full item details easily. Clicking an item in the Equipment list can open a modal overlay or tooltip with the item’s full description, detailed tags, and any custom move or ability. For example, clicking the Ring of Smooshed Chronologies might pop up a small card showing its description and a special move “Chrono-Retcon” with its rules. The interface might show that in a nicely formatted way (name, italicized description, then the move text). Players can read this without leaving the Equipment panel. If the item’s move can be rolled or triggered, the detail view should include a “Roll” or “Use” button for it. In our ring example, the Chrono-Retcon move might require a roll+WIS or just a point spend – the UI would allow the player to perform that move directly from the item’s detail view. (See image for a sample item detail with a custom move and a unique counter). This example shows how a magical ring’s info could be presented: the item’s move is clearly written out, and a tracker for “Paradox Points” is included, illustrating how the UI might handle an item that accumulates charges. By providing such pop-up details, the system ensures even complex item logic is one click away, and the player doesn’t have to flip through a rulebook or notes for their gear’s effects. - Rapid Actions: For items that have immediate use (like a potion or a ration), consider a small “Use” button on the list entry itself. Pressing “Use” could deduct one use from that item’s counter and possibly prompt any outcome (e.g., “heal 10 HP” could prompt the player to adjust HP). If the item is a weapon with ammunition (like arrows), using it might tie into moves (Volley) rather than an item action – that would be handled in the Moves panel, but the Inventory might track ammo count as a separate entry (e.g., “Arrow (Ammo: 3)”). The key is to make common gear interactions (drink potion, mark ration, switch weapon) doable with minimal clicks. - Editing Items: There should be an option to edit item attributes or add notes. Possibly an “Edit” icon on the item detail modal or a toggle to switch the Equipment panel into an edit mode. This allows changing an item’s name, tags, weight, description (for custom or evolving items). Changes should reflect immediately in stats (if weight changed, recalc Load, etc.). This is important for homebrew and flexibility – Dungeon World encourages creative items, so the UI must not be rigid. A player could create a new item here too (though generally new items might be added to inventory first then equipped). - Layout: The Equipment panel might appear as a distinct section on the main screen (if space allows, possibly to the right of the stats). Alternatively, it could be a tab in the central area (like one of the views the user toggles). If using a two-column main view (per the Dribbble concept), the right column might show “Inventory” which could encompass both equipped and carried items. In that case, Equipment might be a sub-section at the top of the inventory list called “Equipped Items” for clarity. Separating them visually (perhaps equipped items listed first under a heading, then a separator, then other inventory) could avoid confusion.
  In summary, the Equipment panel gives immediate access to the gear that affects gameplay. By listing equipped gear with key tags and offering one-click detail views[12][5], players won’t waste time searching for what their sword or magic amulet does. Interactions like equipping or using gear are designed to be fast (drag, click) and seamlessly update the character’s state. This panel ties closely into Dungeon World mechanics: the tags are visible (so if an item is messy or precious the player knows), the Load impact of gear is clearly shown, and any mechanical bonuses (armor, damage) are directly integrated into the character’s stats. It’s a streamlined, interactive equipment list rather than static text, ensuring the player can focus on the fiction and choices, not bookkeeping.
  Inventory Panel
  The Inventory panel covers all of the character’s possessions that are not currently equipped or in use. This is the broader list of gear, loot, and resources the character carries (or has stowed). Key components of this panel:
  • Carried Items List: A scrollable list of items with their details, similar in format to Equipment entries, but typically these are unequipped items. Each entry should show the item’s name, quantity (if multiple), and important tags (including weight). For example: “Adventuring Gear (5 uses, 1 weight)”, “Healing Potion x2 (1 weight total)”, “Coin purse (100 coins, 1 weight)”. Important tags like “uses” or “ammo” should be displayed here as well[12].
  • Weight Calculation: The Inventory panel should display the total weight of all carried items (including equipped ones) and ideally break it down. A small summary at the top might say “Carried Weight: 8 (of 9 Load)” for clarity. Each item’s weight contributes to this; if quantity is more than 1, calculate total weight for that entry (e.g. 3 rations at 1 weight each = 3 weight). This ties into the Load in the Stats panel – ensure consistency by using the same data. If the player toggles carrying something (like dropping an item, or moving it off character), the weight should instantly update.
  • Equip/Unequip Controls: Each item in Inventory likely has a control to equip it. This could be a button (“Equip”) or a drag action as described. Using the control will move the item entry to the Equipment panel (or mark it as equipped). If an item in inventory is not equippable (like coins or generic supplies), the Equip option might not appear. Conversely, items that are equipped (visible in Equipment panel) might be marked differently or not listed here to avoid duplication – or they may remain listed but flagged as “equipped”. One approach: show all items in one Inventory list, with a checkbox or icon indicating equipped status, and filter the Equipment panel from that. However, separating the lists is often clearer for players. Either way, the interaction is straightforward: the player chooses an item and toggles it equipped or not, and the UI handles moving it and updating stats.
  • Add/Remove Items: A “Add Item” button allows the player to add new inventory entries. Clicking it opens a modal or inline form to input item details: name, description, tags, weight, quantity, uses, etc. This is crucial for loot during adventures or creating custom gear. Fields for tags let the player enter keywords (which can be purely reference or could trigger mechanics; e.g., the tag “1 weight” or “Armor 1” might be parsed, but simplest is just to note it). For Dungeon World, common tags include precise things like “ration (5 uses)” or weapon range tags (“near, far”). We should allow multiple tags. The Roll20 sheet has dedicated fields for value, quantity, weight, and a free-form tag field[12]. Our design can similarly provide structured inputs for weight and quantity and a freeform tag text for other tags.
  • Edit Item: Items in inventory can be edited or deleted. Perhaps each entry has a small edit icon, or double-clicking it opens edit mode. This allows corrections and updating uses (if the player uses some adventuring gear, they might go in and reduce uses from 5 to 4, for instance). A delete/trash icon removes the item (possibly with a confirm dialog to avoid accidents). Removing an item subtracts its weight from Load, etc. If the item was equipped, ideally unequip it first or just handle that removal.
  • Item Organization: If the character has lots of items, consider organizational aids. For example, categories or collapsible sections: “Weapons”, “Armor”, “Gear”, “Treasure”. The player could label items by type via a dropdown (like Roll20’s gear type toggle for weapon/armor/item)[13], and the UI groups them. Or simply allow manual reordering (drag items up/down the list) so the player can cluster items as they like. For a single-player tool, flexibility is nice – you might even let the player create custom categories or containers (like a bag vs. on-person). However, at baseline, a simple list sorted by type or name is sufficient.
  • Coin and Currency: Coins (gold pieces, etc.) can be treated as an item (e.g. “Coins – 50”) or a special field. Dungeon World often treats coins as generic currency (with weight: 100 coins = 1 weight). The Inventory panel could display a Coins field where the player enters their coin count, and the system could optionally calculate coin weight (e.g. 50 coins = 0.5 weight, though DW may not need that granularity). For simplicity, we might include coin count as a line in the inventory (with weight if applicable). DungeonPaper mentions tracking coins alongside items[14], so ensure the UI has a spot for currency.
  • Impact on Mechanics: The Inventory’s state directly impacts the Load system. As mentioned, the sum of item weights vs. Load determines if the character is encumbered[9]. The design can visually indicate this on the Inventory panel too – for example, show the weight number in green if under Load, yellow if over Load, red if over Load+2 (mirroring the Stats panel). This duplication is fine because the player might be looking at the Inventory when deciding what to drop. Also, certain moves or tags might depend on inventory (e.g., using Adventuring Gear to produce a needed item), so having a clear view of available gear is important for decision-making.
  • Context Menus & Tooltips: Right-click (or a small context menu) on an inventory item could offer actions: Equip, Edit, Delete, or even “Use” if it’s a consumable. Additionally, hovering over a tag could show a tooltip explanation. For instance, hovering “Dangerous” could show “(Dangerous: GM might cause unexpected harm on use)”. While a single-player likely knows their items, this is helpful for clarity and learning. These little UX touches ensure that even detailed item tags (which are part of DW’s design vocabulary) are not confusing.
  • Integration with Moves: In some cases, using an item invokes a move (for example, using a dungeon ration triggers Make Camp consumption, or using ammo happens via the Volley move). Our system doesn’t fully automate those narrative connections (since a human is presumably still driving the fiction), but we can at least make sure notes or references are handy. For example, an ammo-type item (arrows) could reference the Reload tag or the Volley move in its description. The player can then quickly navigate to the Moves panel if needed. We might implement cross-links, like an item description that mentions a move could be clickable to jump to that move in the Moves panel.
  In essence, the Inventory panel is the management hub for all gear, prioritizing ease of update and clarity of what the character has. By providing quick equip controls, clear display of tags/uses[12], and immediate feedback on encumbrance, the design reduces the “inventory tedium” common in RPGs. Instead of scribbling on paper, the player can reorganize or adjust their inventory in seconds, keeping the focus on the story. The panel is also designed with extensibility in mind: new items can be created freely (supporting homebrew gear), and the system doesn’t assume a fixed item list. This aligns with Dungeon World’s flexibility, where players often create or rename items to fit the fiction. The UI just provides the structure to track those items logically.
  Moves Panel
  The Moves panel is arguably the most important, as Moves are the core of Dungeon World’s gameplay. This panel will list all the moves available to the character and allow the player to quickly reference and perform them. The design should support basic moves (available to everyone), class moves (from the character’s class, including starting moves and advanced moves acquired on level-ups), and any custom or special moves (either added by the player or from external sources like an ongoing campaign move). Key features:
  • Move List Organization: Organize moves into collapsible sections or tabs for easy scanning:
  • Basic Moves: e.g. Hack and Slash, Defy Danger, Volley, Discern Realities, Parley, etc. These are always available. List them together at the top. Since there are not too many basic moves (~8-10 including special moves like End of Session, Make Camp, etc.), they can be listed in a single group.
  • Class Moves: Moves specific to the character’s class (including starting moves and any advanced moves gained). If the character is a Wizard, this includes things like Spellbook (and spell casting moves), Prepare Spells, etc.; if a Fighter, moves like Bend Bars Lift Gates, etc. Group these separately below basics. You could label the section with the class name, e.g. “Fighter Moves”.
  • Racial Moves (if any): Some classes have a race move (e.g. Elf, Dwarf moves). These could be included under class or in their own small section.
  • Custom Moves: Any moves added that don’t fall in the above, such as moves from a compendium class, a campaign-specific move, or a magical effect. These could be listed under an “Other Moves” or “Custom Moves” section. Alternatively, integrate them with class moves but mark as custom (maybe with a "\*" or a note).
  • Special Moves: Dungeon World has general moves like Make Camp, Level Up, End of Session. These might be listed after basics or under a “Special” heading. Since single-player use might involve referencing End of Session and Level Up directly, it’s good to have them in the moves list too (possibly at the bottom as a reminder).
  Collapsible headings help keep this list manageable, so the player can collapse sections not needed in the moment (e.g., they might collapse Basic Moves once they know them well, or collapse Class Moves if not relevant at the time). - Move Entry Display: Each move entry should show at least the move’s name and possibly a short summary or icon indicating its type. For example, “Hack and Slash – (Str) Attack an enemy in melee” or “Discern Realities – (Wis) Closely study a situation”. However, to avoid clutter, the full text of the move can be hidden until expanded or clicked. Show an expand/collapse arrow or a “ℹ️” info button for each move.
  When expanded (or on clicking the move name), display the full move text: the trigger and effect as written. The text can be formatted for readability (maybe italicize the trigger clause, then the results). For instance: - Hack and Slash: When you attack an enemy in melee, roll+STR. On a 10+ you deal damage to the enemy and avoid their attack. On a 7-9 you deal damage but the enemy makes an attack against you. 【This text would be visible when expanded】.
  By default, keep moves collapsed to see more moves at once, and let the player expand the ones they need to read in detail. - Roll Buttons & Automation: Next to moves that involve a dice roll, include a “Roll” button or make the move name itself clickable to roll. For instance, next to Hack and Slash, a small d20 icon or “🎲” button that when clicked will automatically roll 2d6 + STR modifier and produce a result. This uses the stat from the character sheet (so it pulls the current STR mod, factoring any debility). The result can be shown in a dedicated results log area (possibly a panel at the bottom of the screen, or as a temporary overlay message). The output should indicate the move and total, e.g., “Hack and Slash: rolled 9 (STR mod +1, total 10) – Success!”. If possible, highlight the outcome tier (10+ vs 7-9 vs 6-) perhaps in green, yellow, red respectively for quick interpretation. (A future enhancement could even list the general consequence per tier, but the player likely knows or can read the move text.)
  Not all moves require a roll (some are passive or simply hold spending). For those, you might not have a roll button but might still allow the move to be “activated” or expanded. For example, a move like Interrogator (which grants a bonus when using Parley) has no roll of its own; it could just be listed for reference.
  Moves that expend resources (like Cast a Spell requires you to mark off spells, or Commune/Prepare Spells) might trigger additional UI: e.g., after rolling Cast a Spell, the UI could prompt “Did you forget the spell or take -1 forward?” as per the move’s 7-9 outcome. However, that level of logic may be beyond scope – it can be left to the player’s judgment. At minimum, if a move has a complicated result, the full text is there for the player to consult. - Custom Move Support: The system should let the player add custom moves easily, reflecting Dungeon World’s openness to new moves (from compendium classes, magical perils, etc.). A button “Add Move” allows the user to create a new move entry. They can enter the name, description/effects, and optionally tie it to a stat for rolling. For instance, a player might add a compendium class move or a custom move granted by a magic item. Once added, it appears in the list (likely under Custom or in a section the player chooses). This is analogous to Roll20’s sheet where adding a move is just clicking +Add and typing it in[15]. The freedom to add any content (name and freeform text) ensures homebrew moves or modifications are supported. Even the ring’s “Chrono-Retcon” move from earlier could be added as a custom move on the list (though it might also be accessed via the item popup). Some duplication is fine – the player might like it in both places. Modular extensibility is key: new classes or playbooks often come with unique moves, so the design shouldn’t be locked to default moves only[16][17]. - Spell Management (for spellcasters): If the character is a Wizard or Cleric, spellcasting is handled via moves (Prepare Spells, Cast a Spell) and the actual spell list. One approach: treat each spell as a move or attach spells as sub-entries. Another approach is to have a dedicated Spells panel or subsection. Given single-player and no GM, the player might need to track prepared spells. Perhaps within the Moves panel, if the class has spells, include a subsection listing their known spells (each could be like a move entry with name, level, tags, and an effect description). The UI can allow marking a spell as prepared or not, and rolling for Cast a Spell could reference whether it’s prepared. This is complex, so at minimum, allow the player to note spells in their notes or as moves. DungeonPaper mentions integrating moves and spells from the playbook and even letting the user manage them[18], which implies our design should not forget spells. If implementing, you might have a “Spells” tab or let the Moves panel switch to a “Spells” view where spells are listed similarly to moves (with their levels and descriptions). The Moves panel should then provide an interface to manage prepared spells, count of spell slots, etc., likely via manual controls (e.g., checkboxes next to each spell to mark prepared, and a number for how many of each level can be prepared). Given the complexity, you could mark this as a specialized subset of moves available only if the class demands it. - Move Descriptions and Tooltips: Moves often reference basic outcomes or statuses (like “+1 forward” or “hold 3”). It would be user-friendly to highlight keywords in move text and provide tooltips. For example, hover on “hold 3” might show “(Hold: points you can spend for specific effects later)”. This helps newer players. Additionally, if a move references an item or another move (“take +1 forward to Volley”), we could allow cross-referencing. However, this can be excessive – a simpler thing is to ensure the move text in the UI is easily readable (proper line breaks, bold for result clauses, etc.). - Search and Filtering: With many moves, a quick search bar at the top of the Moves panel can be useful (DungeonPaper touts an intuitive search feature for moves/items[19]). The player could type “hack” to instantly filter to Hack and Slash. This is especially helpful for custom-added moves or when a move’s name slips your mind. While not strictly necessary, it significantly improves rapid access to the right move in a pinch. - Triggers and State Ties: The Moves panel mainly reads from character state (stat mods, debilities) to modify rolls. There are a few other state interactions: - If a move grants an ongoing bonus (e.g., some Ranger moves give +1 ongoing in certain situations), the system might not enforce it but the player can use the global modifier toggle or manually remember. - If a move costs resources (like Prepare Spells consumes spell slots, or certain advanced moves cost HP or items), the UI should not automatically deduct those but should remind the player (maybe via the move text or a pop-up). Possibly, after resolving a move, the player will go adjust HP or inventory accordingly. - Some moves give you “Hold” (like Defend, which gives hold points to spend). The interface should remind the player to note those hold points. Our Session Tools includes trackers for hold – one idea is that when a move like Defend is rolled and success, the UI could offer “Add a tracker for Defend hold = 3?” as a convenience. This might be too advanced; alternatively, the player just manually adds a tracker. But designing with this in mind ensures all mechanical bits are accounted for.
  Ultimately, the Moves panel is the control center for game actions. It needs to balance comprehensiveness (listing everything the character can do) with speed (one-click rolls, easy reading). By grouping moves logically and providing roll automation, we let players resolve moves in seconds without losing the narrative flow. The panel keeps all move information connected to the fiction: “Moves define everything your character can try to do” as the Roll20 guide says[20], so our design makes those moves readily available and easy to execute. And since Dungeon World is all about making moves when the fiction demands, the UI’s job is to facilitate that seamlessly – no hunting through papers or PDFs; just click the move, see what happens, and get back to the story.
  Session Tools Panel
  The Session Tools panel is a collection of utilities that assist the player during gameplay. These are not part of the character’s permanent stats, but rather tools for the session’s flow: dice rolling, note-taking, tracking temporary resources, etc. This panel can either be a dedicated screen or (preferably) a collapsible sidebar/drawer that the player toggles open when needed (so it doesn’t clutter the main interface when not in use). Components of this panel include:
  • Dice Roller: A flexible dice rolling interface for any ad-hoc rolls. Dungeon World primarily uses 2d6 for moves and various dice for damage (d4, d6, d8, d10, d12), so presets for those are handy. The roller could have buttons for common rolls like “Roll 2d6” (with maybe a mod prompt if needed), “Roll d8” (for damage), etc. It should also allow custom formulas (for the rare cases, e.g. rolling 1d100 for a random event or 3d6 for stat gen perhaps). A simple UI might be two fields: “NdX + modifier” and a Roll button. Since the Moves panel covers most character-centric rolls, the dice roller is mainly for generic or special rolls: perhaps a random treasure roll, a custom move that requires say 1d4 damage to yourself, or just rolling to simulate something outside character moves. Results from the dice roller should output to the same results log or a pop-up: e.g. “Roll 1d12 = 7”. They might not attach to a move, but the log helps keep a history. Ideally, the dice roller can be used anywhere without switching context (DungeonPaper highlights “Roll dice from any point in the app”[21]). This could mean a minimal dice roller input is always at the top of the screen, or a floating dice icon accessible at all times. But in our design, we put it in the Session Tools drawer – perhaps that drawer can be quickly summoned by a keyboard shortcut (D for dice or similar) for fast access.
  • Note Keeper / Scratchpad: An area for the player to jot down notes during the session. This could be a simple text area labeled “Session Notes” or a more structured list of notes. At minimum, provide a multiline notepad where the player can type anything (NPC names, clues, etc.) and it will autosave. A step up is allowing multiple notes or an ordered log: e.g. a button “Add Note” that creates a timestamped entry. The player could title it and write a snippet. Over the session, they accumulate a list of small notes (which could later be reviewed or archived to the Journal panel after the session). Organized notes help keep track of things without disrupting play[22]. Possibly allow categorization or tags on notes (like mark a note as “clue” or “NPC” or “location”), but that might be more for long-term organization. Since there’s also a Lore/Journal panel for big entries, the Session Notes here can be more immediate and fleeting.
  • Hold/Charge/Counter Trackers: A flexible counter system to track various temporary values that come up in play. For example:
  • Hold: Many moves give hold (Defend gives hold points to spend on defensive actions; certain spells or abilities might give hold as well). The player can create a counter named “Defend – Hold” and set it to 3 when they successfully Defend. Each time they spend 1 hold to do an effect, they decrement the counter. This is easier than trying to remember how many hold remain.
  • Charge or Ammo: If using a piece of equipment that has charges (e.g. a wand with 5 charges) or tracking ammunition beyond the abstract “Volley” move, a counter can track that. For instance, “Arrows” counter starting at say 20, and the player can decrement when they feel it’s used (Dungeon World usually simplifies ammo, but a solo player might choose to track exact arrows for realism).
  • Custom Counters: Essentially, allow the user to add a tracker with a name and either a starting value or a max value. UI-wise, it could be a small list: e.g.,
  o Hold (Defend): [3] (–/+)
  o Blessing Duration: [5] turns (–/+)
  o Torch Light: [3] turns remaining (–/+).
  Each tracker displays its name and current value, with plus/minus buttons to adjust. Optionally, if there’s a logical max, show that (e.g. 0/3 hold spent vs total). If the value hits zero or max, perhaps highlight it. The player will interpret what that means (e.g. hold 0 means none left to spend).
  These trackers are a catch-all for any numeric resource that’s not automatically handled elsewhere. It gives the player a quick way to record things like “3 days travel rations left” or “Spell X ongoing for 1 more minute” etc. It’s up to the player to define them, so the system remains general. - Session Timers & Alarms: If needed, include a simple timer tool. This could be as basic as a stopwatch (counting up time since session start, which some solo players use to log play time) or a countdown (which could be used for timed puzzles or real-time elements). For example, a player might set a 1-hour timer to simulate a time limit in-game. The UI could display it ticking and perhaps flash when time’s up. Another interpretation is “Clocks” (from other PbtA games) – a circle divided into segments to represent impending dangers. While Dungeon World doesn’t formalize clocks, a player could use a tracker for that purpose or an actual visual clock. Since the prompt mentions timers or bookmarks, we can assume a basic timing mechanism: e.g., the ability to press “Start Session” timer and have it record the length of the session (for personal record or pacing). - Bookmarks / Session Markers: A feature to mark significant points in the session. For instance, a “Add Bookmark” button might insert a marker in the notes or log with the current time and allow a label. E.g. “— Scene 2: Entering the Dark Forest (1:05:23 into session) —”. This helps in organizing the journal later or quickly jumping within a long notes document. It could simply be a special kind of note that stands out (maybe bold or a different color). Another use: mark the point where a session ended, so next time you know where to recap from. In a digital platform, you could even link bookmarks to the Journal panel (like session logs separated by bookmarks). - Roll & Event Log: Though not explicitly mentioned, having a log window that displays recent rolls and actions is very useful. This could be part of the Session Tools area or a small always-visible area at the bottom of the screen. Every dice roll (from moves or the dice roller) could print a line here, along with any other automated notes (like “Gained +1 XP” if we automate marking XP on failures, etc.). This log basically functions like the chat in a VTT, except it’s only the player’s logs. The player can refer back to “What was my last Defy Danger roll?” or “How much damage did I take from that trap?”. It also provides context for the notes they take. If not always visible, the Session Tools panel can house a “History” section to review past rolls/events.
  The Session Tools are designed to streamline the housekeeping part of the game. Dungeon World’s rules are relatively light, but a solo player benefits from tools that a GM might otherwise help with: tracking ongoing effects, reminding of time, etc. By bundling these in one panel, we ensure they’re accessible but not in the way. The player can pop open the Tools drawer, make a quick note or roll, then hide it to get back to the action.
  All these tools emphasize speed and clarity: - The dice roller saves time over physical dice, and being able to roll from anywhere (even a quick keyboard shortcut) means the player’s attention stays on the game[21]. - The notes and trackers reduce cognitive load – the player doesn’t have to remember every detail or hold in their head; they can externalize it in the app. - The design for these should be clean and minimal (e.g., a simple list of trackers, simple text notes area) to avoid distracting visuals. It’s utility over style here.
  Finally, consider a bit of integration: If the player fails a move roll (6- result), Dungeon World grants +1 XP. The system could detect that and, in the log or a subtle pop-up, say “Mark XP for failed roll.” Possibly even increment the XP counter automatically (with an option to undo). This crosses between Moves and Session Tools (since it’s an automated rule tracking). It’s an example of how the digital platform can assist the gameplay by catching things a player might forget. As this is a complex feature, it could be optional or simply a reminder rather than an automatic add. The key is that the tools can help enforce Dungeon World’s little mechanics (like fail = XP) to keep the flow smooth.
  Lore / Journal Panel (Optional)
  As an optional but useful addition, a Lore or Journal panel provides a place to record long-form information and past events, separate from the quick session notes. This panel is essentially the character’s chronicle and reference library:
  • Session Logs / Journal Entries: The player can maintain a running log of what happened each session or adventure. For instance, entries could be dated or numbered by session: “Session 5 – Delving into the Mysterious Cave: [text…]”. Each entry might be created at the end of a play session (perhaps summarizing major events, loot, XP gained, etc.). Over time, this forms a history that the player can review to recall previous plot points. Unlike the scratchpad notes, these entries are more permanent and narrative-focused. The UI can list them in reverse chronological order with titles and creation dates.
  • World Lore and Reference: This could also be a place to store information about the game world relevant to the character. For example, notable NPCs, locations, quests, or lore tidbits the character has learned. The panel might allow categories or a tree: e.g., an NPC section where the player maintains a list of NPC names and descriptions, a Quests section for current and completed quests, etc. This is more free-form and up to the player to utilize, but a structure (like headings and sub-notes) can keep it organized.
  • Formatting and Rich Text: To differentiate from quick notes, the Journal could support richer text formatting – bold, italics, bullet points – so the player can make more readable entries. For instance, they could bold NPC names or make a bullet list of loot items found today. Even images could be allowed (perhaps they paste a map or a symbol encountered). However, as a design focusing on structure over aesthetics, we can keep it simple yet allow some markup for clarity.
  • Integration with Gameplay: The Journal is mostly reference, so it might not directly affect mechanics. But it can tie in subtly. For example, the End of Session move in Dungeon World asks questions like “Did we learn something new and important about the world?”[23] – the player could quickly scan their journal entry to answer that. In fact, the UI could prompt the player at end-of-session (when they click that move) to write a quick journal entry or summary. Possibly, after the player marks XP for the session’s questions, the app can say “Write a log entry for what happened?” to encourage usage. This ensures that the lore panel stays up-to-date as a living record.
  • Bonds and Alignment Tracking: If not placed in the Stats panel, the journal is a logical place to track Bonds (since bonds are like relationship lore) and Alignment notes (the specific tenet that gives XP). For bonds, a simple list of bond statements can be kept, with a checkbox or strikeout for resolved bonds. After each session, the player can review bonds here to see if one was resolved (and if yes, mark XP and possibly remove or replace it). Since this is optional, we might have just a section in the journal for it. DungeonPaper emphasizes tracking bonds and flags as part of notes[10], indicating those are often treated as part of the narrative record.
  • Searchable Reference: As the campaign grows, the journal could become lengthy. Implementing a search function (or at least a find-in-page) helps the player quickly find, say, the mention of “Baron Threl” or “magic sword” they wrote months ago. This is a quality-of-life addition for deep campaigns.
  • Extensibility: The journal is inherently extensible because it’s user-created content. The player can write whatever they need. For future homebrew needs, they might even create reference sections for new rules or custom mechanics. For example, if the campaign has a unique magic subsystem, they could jot down how it works in the lore panel for reference. Our design should not restrict what they can write or how they organize too strictly – provide templates or section headers but allow customization.
  Though optional, this panel greatly enhances long-term usability of the platform for Dungeon World campaigns. It ensures that important story and world details are preserved and easily accessible, which is crucial in a game that’s emergent and co-created. It also offloads memory work from the player – they have a reliable place to check “What was that prophecy we heard?” or “Who is indebted to me?”. By keeping it separate from the main mechanics panels, the player can focus on mechanics during play and on storytelling between or after sessions.
  Interaction Design & Behaviors
  This section details how the user interacts with and between panels, and what dynamic behaviors the interface supports to maintain clarity and speed:
  • Synchronized Data Across Panels: All panels are interconnected under the hood, reflecting a single character state. Changes in one panel should instantly propagate to others where relevant. For example, if the player equips an item (moves it from Inventory to Equipment), the Stats panel’s Load and Armor should update immediately (since weight carried and armor value may change)[24][5]. Similarly, if the player checks a Debility in the Stats panel, any moves that use that stat will roll with the updated modifier (this can be automatic because the stat mod value changed). This synchronization ensures the player trusts the interface – any adjustment is accurately applied everywhere.
  • Click-to-Equip / Unequip: Equipping and unequipping are common actions linking Inventory and Equipment. We’ve made it one click (or drag-drop) to perform. The behavior can be: clicking “Equip” on an inventory item will remove it from the inventory list and add it to the equipped list. If the Equipment panel is visible, one might see it appear there; if not, at least an icon or message confirms it. The reverse for unequip. These actions also likely toggle some property in the item’s data (e.g. an “equipped” flag). If for some reason the design opts for a single list with checkboxes for equipped, then clicking the checkbox itself is the action. In any case, the UI should give immediate feedback: perhaps the item entry highlights or animates to the new panel, and a small toast message might say “Equipped: Longsword (Damage +1 applied)”. By doing this, the user is confident that the action happened and knows any mechanical effect (like the +1 damage) is now in play.
  • Drag-and-Drop Behavior: While not strictly necessary, drag-and-drop can make the interface feel more natural. Potential uses:
  • Inventory Management: Drag items to reorder them in the list (for the player’s visual preference). Drag item onto Equipment section to equip. Drag off equipment to inventory to unequip. Possibly drag an item onto a “trash” icon to delete (with confirm).
  • Reordering Moves or Notes: The player might rearrange moves (maybe put their frequently used moves on top). Allow drag sorting of moves within their categories. Similarly, rearrange notes or trackers if needed.
  • Dice Drag to Notes: A fun idea is if the player could drag a dice result from the log into a note, but that’s extra – not core.
  • If implementing drag, use ghost images/cursor change to show the user what action will occur (e.g., dragging an item over the Equipment panel could highlight the panel to indicate “drop to equip”).
  Of course, all these also have alternate non-drag methods for accessibility (buttons or context menus). - Modal Overlays for Details: When the user needs more information or a deeper interaction, modals and pop-ups are employed: - Item Detail Modal: As described, clicking an item yields a modal with full info and possibly action buttons. The modal should appear center-screen or near the item’s location (to seem contextual), and darken the background for focus. It must have a clear close button (X) or just clicking outside to close, to ensure quick return to the main view. The modal can also be used for editing item fields if in edit mode. - Move Detail Popup: If the move text is long, expanding it could effectively be a pop-up or inline expansion. Some UI libraries allow a hovering card on click/hover. Since Dungeon World moves are not extremely long (usually a few sentences), an inline expansion might suffice, but for consistency, a modal could also be used (like clicking a move name opens a modal with the full description and a roll button). - Custom Move Explanations from Items: If an item references a move or has a unique effect (like our ring example), clicking perhaps a “?” icon on the item entry could directly open a modal explaining that move or effect. This is similar to above but highlights that an item’s special abilities might be documented in a modal. - Editing Forms: Any time the user adds/edits something (item, move, note), consider a modal or an in-panel form. Modals are nice for focus – e.g., “Add Item” opens a modal form, the background dims, the user fills fields and saves. This prevents distractions and ensures they complete the input. Once saved, the modal disappears and the updated list is behind it. - Confirmation Dialogs: Small modals for confirming destructive actions (deleting an item or note) are important to prevent mistakes. A simple “Are you sure? Yes/No” is fine.
  Modal design should stay minimalist and consistent: likely use the same style for all (perhaps the same pop-up card component). - Drawer for Tools: The Session Tools being a right-side drawer means it slides over or from the edge. The user toggles it via a button (maybe an icon of a toolbox or dice). The behavior: clicking the toggle either pushes the main layout left a bit or overlays on top (depending on implementation). The drawer should have a close button as well. Inside, the tools (dice roller, notes, etc.) could be organized with tabs or just one after another vertically with headings (Dice, Notes, Trackers...). Since screen width on desktop is usually ample, opening the drawer can cover perhaps 25% of the width without hiding too much of the main area. The idea is the player can glances at main info even while using a tool. For example, they might keep an eye on their HP (left sidebar) while using the dice roller in the right drawer. - Hover Behaviors and Tooltips: Use hover tooltips to keep the interface clean yet informative: - Stat Abbreviations: Hover over “STR” shows “Strength” and maybe the full description if any. - Debility Checkboxes: Hover over “Weak” shows “-1 STR modifier (due to debility)”. - Item Tags: Hover over item tags like “Precious” or “Messy” to show their game meaning (some players might not recall every tag definition). - Move outcomes or keywords: Hover over “+1 forward” text might show “Applies to next applicable roll”. - Icons: If using icons (HP heart, XP star, etc.), hover can show the label (“Hit Points”).
  These tooltips should be short (a sentence or less) and purely explanatory. They vanish on mouseout. This way, the UI can use symbols or short text for brevity but still educate or remind the player of details on hover. It’s especially helpful for new Dungeon World players who might not remember what “1 weight” implies for encumbrance, etc. - Right-Click Context Menus: For power users, right-clicking elements can bring up context menus with relevant actions. For instance: - Right-click an inventory item: menu = Equip/Use/Edit/Delete. - Right-click an equipped item: menu = Unequip/Use/Edit. - Right-click a move: menu = Roll/View/Edit (if custom moves editable). - Right-click a note: menu = Edit/Delete.
  This isn’t necessary if UI buttons are present, but it adds a layer of convenience and is typical of desktop applications. It leverages desktop norms (since we are desktop-optimized) where right-click is expected to do something. Just ensure it’s not the only way to do an action. - Keyboard Shortcuts: Mentioning hotkeys can elevate the user experience for advanced users. Some possibilities: - Number keys or function keys to switch main panels (e.g. F1 = Stats, F2 = Moves, F3 = Inventory, etc., or 1 for Stats, 2 for Moves… if those aren’t used elsewhere). - A dedicated key to open the Dice Roller (maybe R for roll or D for dice). - Perhaps arrow keys or J/K to move through move list, Enter to roll, etc., for those who prefer keyboard. - Ctrl+N could open a new note, etc.
  These should be optional enhancements – the UI is fully usable by mouse alone. But calling them out in documentation or an on-screen cheat sheet (maybe accessible via a “?” help icon) would be helpful for those who want rapid navigation. - Panel Switching Behavior: If using tabs or buttons to change the central panel, the transition should be quick and preserve state. For example, if a user was scrolling through Inventory and then switches to Moves and back, the Inventory panel could remember its scroll position or any expanded item. This way the user doesn’t feel like each switch is a “reset”. On desktop this is easier (we can keep components mounted).
  Alternatively, some panels could show simultaneously if screen width allows (e.g., Stats on left, maybe Moves main, and a mini Inventory on right). But that can get cramped; better to let the user choose what they want visible. Possibly a multi-column layout could allow, say, Moves and Inventory side by side in the main area if the user expands the window very large – that’s an advanced responsive design idea (perhaps dragging panel borders to resize). However, initial design can keep it one-at-a-time for simplicity, since we do have the always-on Stats sidebar. - Visual Feedback and Clarity: All interactive elements should give feedback: buttons highlight on hover, depressed state on click, etc. Drag items should show a ghost. When a value changes (HP goes down, XP goes up), consider a brief highlight or flash on that field to draw attention. For example, if the player clicks a damage roll and it outputs “7 damage” and they then subtract 7 HP via a quick button, the HP value could animate from old to new or glow red briefly to indicate “HP changed!”. This helps connect cause and effect, especially if some automation is present (like if a move’s result automatically deducted HP, you’d want the user to notice). - Multi-step Workflows as Overlays: Some tasks might involve multiple steps. For example, leveling up: when XP threshold is reached and the player triggers the Level Up move, the system could guide them: show a modal “Level Up: Increase your level by 1 (to 4). Spend XP (reduce XP by (level+7)). Choose one new move from your class list. Increase one stat by +1.” This sequence can be done within one modal with a form or sequential prompts. The UI can assist by presenting the choices (maybe listing the available advanced moves to pick from, and a dropdown for which stat to raise). While the player can do all this manually, providing a structured workflow ensures nothing is forgotten. After completion, the modal could auto-update the character (Level field +1, XP subtract, new move added to Moves panel, stat increased). This is a significant convenience and reduces errors in bookkeeping. If not fully automated, at least listing out the steps as a checklist in the Level Up modal is helpful. Dungeon World’s level-up is straightforward, so coding it is feasible.
  Another example of multi-step: End of Session. Pressing an “End Session” button (or just going through the move text) could open a panel that asks the end-of-session questions. The player checks yes/no for each: - “Learned something new about the world? [Yes/No]” - “Overcame a notable enemy? [Y/N]” - “Looted a memorable treasure? [Y/N]”
  The interface then says “You answered X yes, mark X XP.” Perhaps even auto-add that XP. And possibly remind to resolve bonds and alignment (with a space to mark those XP if applicable). This interactive approach turns the often overlooked end-of-session procedure into a quick, guided form, ensuring the player doesn’t skip the chance to get XP[23]. It’s an example of the UI following Dungeon World’s rules to help the single player replicate the around-the-table checklist experience. - Saving and Loading State: While not a direct user interaction, it’s worth noting that all these panels and data represent a character sheet that should persist and be loadable. There should be an easy way to save the character (likely automatically to local or cloud storage after any change) and to export/import if needed (for backup or sharing). DungeonPaper mentions exporting custom content[25], similarly our platform could allow exporting the whole character (JSON or other format) for safekeeping or transferring to another device. This is a behind-the-scenes behavior but critical for a good user experience (no one wants to lose their campaign info due to a crash).
  In summary, the interaction design focuses on making every common action one or two clicks at most, with clear feedback. Panels interact seamlessly, sharing data so the player perceives it as one cohesive dashboard rather than disparate screens. Modals and overlays provide depth on demand, without taking the user away from the main flow. Hover and contextual tools enrich the experience by providing info and alternate controls in a non-intrusive way. All these behaviors align with the needs of a Dungeon World player: they can swiftly equip a sword mid-battle, roll for a move, jot a quick note about a clue, and check an item’s effect, all without flipping through multiple pages or losing track of the action. The interface becomes a trusted assistant in play, handling the fiddly bits while the player focuses on the narrative and choices.
  Session Workflow Design
  To illustrate how all these pieces come together, let’s walk through a typical use of the system across a game session, highlighting how a player would flow through various panels and actions:
  Before the Session (Prep Phase):
  When the player sits down to start a session, they’ll use the interface to get everything in order: 1. Review & Update Character: The player glances over the Stats & Health panel (always visible) to ensure everything is up-to-date. They confirm HP is fully healed if last session ended at a camp, check their XP (maybe they leveled up last time and need to apply that now if not already done), and verify debilities (clearing any that were healed between sessions). They might use the interface to heal or mark recovery: e.g., if they made camp, they update HP or uncheck a debility box. 2. Gear Up: In the Inventory panel, the player reviews their items. If they plan to start with different equipment (maybe this session is in town, so heavy armor is unequipped), they use the equip/unequip controls to adjust. For example, they unequip a sword and equip an axe instead. The interface updates the Equipment list and stats accordingly. They ensure important adventuring gear is listed (adding any new items they bought or found at the end of last session via “Add Item”). If encumbrance is a concern, they check the Load display – if it’s over the limit, they might decide to leave something behind (and they can delete or mark an item as stashed, perhaps by just unequipping it and conceptually not carrying it). 3. Set Session Tools: The player opens the Session Tools drawer to set up any trackers or notes for the upcoming play. For instance, if they know there’s a countdown until an event (say, “the ritual completes in 5 hours”), they might add a tracker “Ritual Timer: 5” or start a timer. Or if they have a buff spell active from last session (e.g., “Stoneskin spell, 2 armor remaining”), they add a tracker for that. They might also create a quick note like “Goals: Find the lost key, Avoid the dragon” as a reminder of objectives. This prep ensures when the action starts, they aren’t scrambling to note these things. 4. Recall Last Session: The player might quickly pop open the Journal panel to read their last entry or notes. This refreshes their memory on the story: e.g., they read “Session 7: We entered the dungeon, fought goblins, found a strange key.” With that context, they’re ready to continue. If they notice something in notes (like an NPC name) they need on hand, they could copy it to a sticky note in the Session Tools or just keep Journal open on a second monitor if they have one. The design should allow the Journal to be open concurrently if needed, though it’s fine if they just open and close it as needed. 5. Spells Preparation (if applicable): If the character is a spellcaster and this is a new day in-game, they use the Moves/Spells panel to prepare spells. For example, a Cleric would open their Spells list, check off which rotes and spells are prepared. The interface might provide checkboxes for prepared spells, and possibly a counter of total levels prepared. The player marks these and the system could sum up “Prepared: 3/3 levels” or similar. This way, as play begins, the Moves panel accurately reflects what spells can be cast. 6. Starting the Session Timer: The player might hit a “Start Session” button or otherwise mark the beginning of play (optionally). This could simply be for their personal log, recording a timestamp for later journal writing or just knowing how long they played.
  Now the groundwork is laid; the player has essentially used the interface to get their character sheet and tools in a ready state, mirroring how one might shuffle papers and get dice out on a real table.
  During the Session (Action Phase):
  As the game unfolds, the player will rapidly switch between looking at moves, rolling dice, and updating the character state. The interface supports this with minimal friction: 1. Making Moves: Whenever the player character does something requiring a roll, the player goes to the Moves panel (if not already on it). Often, they’ll keep the Moves panel open for much of play because that’s where the action resolution lives. Suppose the character enters a duel and strikes the enemy – the player clicks “Hack and Slash”. Immediately, the system rolls 2d6 + STR. The results log might show “Hack and Slash: 4 + 2 (STR) = 6”. The interface could highlight this as a failure (e.g., red text or an “✗”). The player recalls (or sees in the expanded move text) that a 6- means the GM makes a move. Since it’s solo, the player might interpret what happens. Importantly, the system notices a miss: it can prompt or automatically add 1 XP for the failure (maybe a small XP icon blinks). The player sees the XP count go from 2 to 3 and perhaps a note “Failure! Mark XP.”[23]. This gentle automation keeps the session flowing and rewards consistent. 2. Applying Outcomes: After a move, the player might need to adjust stats. In the Hack and Slash example, on a 6- the character likely takes damage from the enemy. The GM (if external) or solo engine says “you take 1d8 damage”. The player uses the Dice Roller quick input to roll 1d8, or if the enemy’s damage is known (say d8), maybe they have a custom entry to roll that. The dice roller outputs a 5. The player then clicks a “-HP” button 5 times or enters the new HP value. HP in the Stats panel updates from, say, 18 down to 13. The HP field flashes or turns red briefly to indicate a loss. If HP drops to 0 or below at any point, the system would immediately flag that (“HP is 0 – Last Breath move triggered!”). Perhaps it automatically opens the Last Breath move text or at least signals the user strongly (maybe the HP display turns skull-colored and a pop-up says “You are dying! (Last Breath)”). The player can then execute that move. 3. Using Items Mid-Game: The fight continues; now the character decides to quaff a healing potion. The player opens the Equipment panel (or if it’s visible side-by-side, just looks there) and sees “Healing Potion (1 use)”. They click “Use”. The system might pop a modal confirming use and showing any effect (“Heal 10 HP”). The player confirms, the potion’s uses drop to 0 and it might either gray out or disappear (if we assume it’s consumed). They then adjust HP up by the appropriate amount (either manually or the system could offer to do it: e.g., after using, a prompt “+10 HP?” could appear). The interface’s goal is to cut down the steps: ideally “Use” could automatically restore HP and remove the item, but confirming is safer. After healing, HP is updated (highlighting the increase in green perhaps).
  If the potion was in Inventory and not equipped, the player would have to fetch it – maybe they open Inventory, find it, and hit “Use from inventory”. This suggests maybe important consumables should be equipped or a dedicated quick-access consumables bar might be useful. But assuming they prepared by equipping it, it’s fast. 4. Switching Contexts: The player may need to reference different info quickly. For example, after the battle, they want to discern realities. That’s a move (Wisdom) – they hit “Discern Realities” roll. Then they ask questions. To answer, they recall a detail from a previous clue. They quickly open the Notes in Session Tools to see the clue they wrote (“the runes on the altar…”) or search the Journal for “altar”. They find the info, which informs their next move. This shows how the player can hop between Moves (to roll) and notes (to recall lore) swiftly. Our design with persistent Stats and the drawer for notes means they didn’t lose sight of HP or the fact they have that one hold from Defend still on a tracker, etc., while checking notes. 5. Dynamic Tracking: Suppose the character took the Defend move earlier to protect an ally (or in solo, maybe an NPC ally). They rolled Defend and got a partial, giving them hold 1. The player uses a Tracker to note “Defend hold: 1”. Later, when an attack comes in, they decide to spend that hold to reduce damage. They click the tracker’s minus, dropping it to 0, and describe how they blocked the blow. The tracker hitting 0 might highlight or auto-delete itself (maybe it stays until end of scene or user removal). This reminds the player that resource is now expended.
  Another dynamic element: ongoing status. If a move or monster gave them a condition (not a DW debility, but say “on fire” or “cursed”), the player might note it in a tracker or note. They might even add a custom Debility if it fits, but more likely just a note like “Ongoing -1 to INT from curse” and perhaps use the global modifier toggle. The interface is flexible enough to handle these narrative wrinkles via the notes/trackers without needing a special module for each possible condition. 6. Continuous Logging: Throughout this, the log records key rolls: “Discern Realities: 7 (partial)”, “1d8 damage roll = 5”, “Last Breath: 11 (success)”, etc. The player can scroll this log if needed to recall what just happened. This is especially helpful in solo play where they might step away or pause and come back, and need to remember what the last action was. 7. Hotkeys for Speed: As the player grows familiar, they might use hotkeys: e.g., press “I” to open Inventory when looting a treasure, press “N” to quickly open Notes and jot “Found a golden idol worth 500 coin”, then press “M” to get back to Moves. They don’t need to, but if they do, it makes things even smoother. The UI should not require a flurry of mouse actions for repetitive tasks; once learned, keyboard could expedite things like adding XP (maybe a hotkey to +XP, though accidental could be risky). 8. Emergencies and Modal Focus: If at some point a big modal pops up (like an item detail or level up), the workflow might pause. The player deals with that (e.g., leveling up mid-session due to sudden XP gain). They use the modal to handle it, then return to the action. Because our design tries to avoid multi-step tasks during intense action (level up normally is done during Make Camp or downtime, not mid-battle), we anticipate most modals (except quick reference ones) happening in calmer moments. Still, the interface can handle it – e.g., if the player hits level in the middle of a dungeon, they might just note “XP filled” and level up later, or if they want, do it via the interface on the spot with a guided prompt. 9. Collaboration (if any): While it’s single-player, if the player is actually playing with a GM over voice, the interface can help share info. They might read out from the sheet or if using a screen share, show the relevant panel. But since no direct GM integration, we skip that – the important part is the player can get whatever info the GM asks (“How much HP do you have? 13.”, “What’s your Dex? +2.”, “What gear are you carrying? Let me check inventory…” – all readily visible).
  During the session, the player is essentially cycling between Moves (to do things), Stats (to monitor status), Inventory/Equipment (to manage resources as needed), and Tools (to note or roll odd things). Our design allows these to be accessed with minimal friction and often without needing to fully close one to see the other (given the persistent stat sidebar and quick drawers). This keeps the focus on the fiction and decisions; the interface is a background facilitator.
  End of Session (Wrap-up Phase):
  At session’s end (which might be a dramatic cliffhanger or just a natural stopping point), Dungeon World has specific moves and bookkeeping: 1. End of Session Move: The player opens the Moves panel and finds “End of Session” (likely under Special Moves). To make this easy, we could have a dedicated “End Session” button visible when the session timer is stopped or just always accessible. Clicking it could bring up the End of Session dialog. The UI then walks the player through: - Listing their current Bonds and asking if any were resolved. The player checks any that are resolved. For each, they mark +1 XP (the system could add these XP automatically once confirmed). - Show the character’s Alignment goal and ask if it was fulfilled this session. If yes, mark +1 XP. - Then present the three standard questions (new knowledge, notable enemy, memorable treasure)[26]. The player answers Yes or No to each. For each Yes, mark +1 XP. - Tally the XP from these (bonds + alignment + questions) and add to the XP total. The UI might say “End of session: you earned 3 XP” and update the XP display. - If the platform is keeping a session log, it could record these answers or at least the XP gained. 2. Level Up (if applicable): After adding session XP, the system checks if the character’s XP >= Level+7[7]. If so, a Level Up modal or prompt appears: “You have enough XP to level up! Would you like to Level Up now?” If the player says yes, it goes through the level-up sequence (increase level, spend XP by resetting to 0 or subtracting level+7, choose a new move, increase a stat, etc., as described earlier). The Moves panel is likely used here to pick the new move (perhaps it shows a list of available moves from the class that aren’t taken, if we have that data; otherwise the player might type in the new move via Add Move). - If the player chooses to level up later (maybe they want to do it at the start of next session instead), they can dismiss the prompt. The system might then highlight the Level Up move or just keep an indicator on screen (like “Level up available!” icon) as a reminder. - Assuming they go through with it, the Stats panel now shows Level+1, XP reset to whatever remainder (DW says set XP to 0 and carry over excess, depending on interpretation, but usually just subtract required XP). The new move is added to Moves, and one stat is incremented (which might automatically adjust its modifier and max HP if the class dictates, etc. The system could recalc Max HP if DW uses level for that—actually in DW, HP is class base + Con, so leveling doesn’t increase HP unless Con increased, unlike D&D. So that’s simpler). - The interface ensures all these changes persist. 3. Update Journal: With the mechanical stuff done, the player likely writes a journal entry for the session. They switch to the Journal panel and create a new entry for Session X, summarizing what happened, what they achieved, any loose ends. The interface provides a nice text area to do so. They might copy some notes from the scratchpad here into a coherent narrative. Because the interface logged dice and events, the player could scroll the log to recall key events, and their notes help recall details like NPC names. - If the platform wanted to be fancy, it could automatically append a basic log of moves to the journal entry, but that may be overkill. It’s better if the player writes it in their own words. 4. Cleanup: The player might tidy up the interface for next time: - Archive or clear the session notes scratchpad if they don’t need it (or maybe they keep it; some might clear it to start fresh next time). - Reset any trackers that don’t carry over (e.g., if a tracker was just for this session’s scene or a countdown that’s now moot, they remove it). - Check off that any one-time buffs or effects have ended (maybe removing those trackers or un-equipping a temporary magic effect). - Ensure their inventory is updated if they gained loot. They might add new items now if they didn’t during play (e.g., “Add item: Golden Idol, value 500, 1 weight”). - If they used consumables, verify uses are accurate (maybe they drank 2 out of 5 uses of adventuring gear, they adjust that). - They might also use this time to rearrange moves if they gained a new one (maybe put the new move into an appropriate category or order). 5. Save and Exit: The system should auto-save, but if there’s a manual save or export, the player does that just in case. They close the session timer if one was running (could automatically stop when End Session was triggered).
  This workflow shows the life cycle of a play session with our control panel: from preparation, through the heat of action, to the reflective end. Throughout, the design supports the player’s needs: - Pre-game prep was made easy by clearly separated panels (no confusion where to find stats vs gear vs moves). - Mid-game actions were streamlined with one-click rolls, easy stat updates, and quick references. - End-game bookkeeping was aided by automated prompts and a structured process, turning what can be an overlooked chore into a guided task that ensures the player gets their XP and updates their character properly, staying true to Dungeon World’s procedures.
  The single-player assumption actually let us enhance some aspects: e.g., automating XP-on-miss and guiding end-of-session. In a multiplayer environment, a GM usually handles some of that, but here the system itself can take on a bit of the GM’s reminder role. We still keep the player in control (they ultimately decide when to mark XP or level up), but the UI nudges them according to the rules.
  Importantly, at every phase the speed of access to information was prioritized: - No hunting through a PDF for a move text – it’s right there in the Moves panel. - No manual math for modifiers or encumbrance – the sheet auto-calculates and signals when needed. - One click to roll dice – no manual typing unless they want something custom. - End of session handled in one flow – no flipping pages or forgetting questions.
  This way, the player spends the majority of their time thinking about the story and choices, not manipulating the interface. The interface just augments their memory and handles the rules bookkeeping in the background.
  Developer-Ready Summary
  Below is a technical summary of the proposed system, breaking down each panel/component, their data structures, interactions, and state dependencies. This is intended for the development team to identify implementation requirements and ensure consistency with Dungeon World mechanics:

1. Layout & Framework
   • Main Container: A single-page application layout with a persistent sidebar (left), a central content area, and an optional side drawer (right). Use a responsive grid or flex layout:
   • Left Sidebar (Stats Panel) – fixed width column containing character vitals (detailed in Stats section).
   • Center Panel – dynamic content area that swaps between different views (Character Details, Moves, Inventory, etc.) based on user selection.
   • Right Drawer (Session Tools) – a hidden panel that slides out on demand. Overlays on top of the center panel or pushes it, depending on UX choice.
   • Navigation: Could be a top nav bar or tabs. Each core panel (Stats, Moves, Inventory, etc.) is a route or component that can be shown in the center. The left sidebar is always rendered. The right drawer is always present but toggled.
   • State Management: Use a centralized state store (or context) to hold character data (stats, items, moves, etc.) so that all components see updated values. This state likely mirrors a Character sheet object:
   character = {
   name, level, class, alignment,
   stats: { STR: {score: X, mod: Y, debility: false}, DEX: {...}, ... },
   HP: { current, max },
   XP: currentXP,
   load: { currentWeight, maxWeight },
   armor: currentArmor,
   damageDie: "dX",
   moves: [ { name, description, stat: "STR" (if rollable), isBasic: bool, isClass: bool, etc. } ],
   spells: [ similar structure if needed ],
   inventory: [ { name, quantity, weight, tags: [], equipped: bool, uses: maybe, description, type: "weapon/armor/item" } ],
   notes: "freeform notes text or list of note objects",
   journal: [ { title, date, content } ],
   trackers: [ { title, current, max (optional) } ],
   // plus possibly settings like global roll modifier, etc.
   }
   This object should be serializable for saving.
   • Theme & Styling: Emphasize readability: use a clean font, distinguish headers vs content, and color-code where helpful (HP in red, XP in gold, etc., consistent with common RPG UI). But keep aesthetic elements minimal (no overly ornate backgrounds that could clutter).
2. Character Stats & Health Panel (Left Sidebar Component)
   • Data Displayed: Character name, class, level, alignment (alignment could be split into alignment type and alignment statement). Stats (STR, DEX, CON, INT, WIS, CHA) with each stat’s score and modifier (modifier can be derived as Math.floor((score-10)/2) if using D&D formula, but Dungeon World uses a specific table of scores to mods[27]; better to use a lookup or calculate similarly). Alternatively, store mod explicitly in state for simplicity.
   • Debilities: an array or object mapping stat to a debility flag. If debilities.STR = true, then STR mod is effectively one less. Implementation: either calculate on the fly (mod = baseMod - (debility? 1:0)) or adjust the mod in state when debility toggles.
   • HP: store hpCurrent and hpMax. Possibly also track hpTemp if any (DW usually doesn’t have temp HP, so ignore).
   • Armor: can be stored or computed. Likely stored as armor in state, updated by equipping armor pieces or moves.
   • Damage Die: store as a string (e.g. "d10"). Set on class selection (each class has a default damage die) but allow override in case of moves like the Fighter’s “Merciless” which adds damage (that might be handled via a global modifier or by adjusting how damage is rolled).
   • Load: maxLoad = class base + STR mod[8] (class base could be stored in class data or even in a move/tag). currentWeight = sum of all inventory items’ weight _ quantity (summing either all items or just those with equipped + not equipped, but since all count, just sum all inventory where carried).
   • We might maintain a live calculation or update currentWeight whenever inventory changes. Could also precompute each item’s total weight (weight _ qty) and sum.
   • Encumbrance states: derive booleans for isEncumbered = currentWeight > maxLoad and isOverburdened = currentWeight > maxLoad + 2. Alternatively, derive an encumbranceLevel (0 = normal, 1 = encumbered, 2 = overburdened) for use in UI. These thresholds are from DW rules[9].
   • XP: store as integer. levelUpThreshold = level + 7. The UI can compare XP with threshold to suggest level-up.
   • UI Elements:
   • Labels for each stat with a small input or display for score and mod. The mod might be clickable (button) to roll, so implement each mod value as a button element with an onClick -> call roll2d6(mod).
   • Debility checkboxes next to each stat: onChange triggers toggling that stat’s debility in state. Also triggers recalculation of that stat’s effective mod (if calculated on fly, the UI component that displays mod will recompute from state; if storing mod, then toggling could just subtract 1 from mod and store, but better to compute).
   • HP displayed with an editable field or two fields (current and max). Could use a slider or just up/down buttons:
   o Decrease HP button: onClick subtracts 1 (with min 0).
   o Increase HP button similarly.
   o Also allow direct typing in current HP field for when larger changes happen.
   o When currentHP <= 0, trigger some callback (maybe open Last Breath dialog or flag a state like needsLastBreath = true to prompt user).
   • XP display: probably just text “XP: X/Y”. Might also be clickable to add XP (like a “+” button to increment XP when a miss happens or end of session awards – though those can be automated or done via context menu as well).
   • If XP >= threshold, perhaps show a Level Up button here or highlight XP text. An onClick to that would call the level-up function/workflow.
   • Armor display: just a label or disabled input showing current armor value.
   • Load display: e.g. “Load 5/9”. Possibly colored based on encumbrance state. Implement by checking encumbrance state from state as above. If encumbered, add a warning icon or color.
   • Other: If adding bonds/alignment here, could include a small text or icon that when clicked shows them. But likely skip in this panel except alignment maybe static text.
   • Global Roll Modifier (Forward modifier): If included, UI could be a radio or dropdown as described. This would sit maybe below XP or at bottom of sidebar. It would set a state like globalRollMod = 1, 0, -1 or custom and the roller function would include it. Also a field for holdModifier if we allow adding hold as mod (like Roll20’s special hold feature)[11]. But this is optional.
   • Dependencies & Calculations:
   • Debility affects stat mod: ensure wherever mod is used (move rolls, etc.) it pulls from effective mod.
   • Armor value depends on equipped items and possibly moves (some moves grant armor). So when equipment changes or relevant move toggles, recalc armor. Implementation: either calculate armor on the fly from inventory (sum all equipped items with armor tags + any temp bonuses) or maintain an armor field updated by events (e.g., equipping an item dispatches an update to armor). The Roll20 sheet auto-calculates from equipped gear[4], we should too.
   • Load max depends on STR mod and class. So any change to STR mod or class base load should update maxLoad. We’ll need a data structure for classes (e.g., Fighter base load 12, etc.) or store base load as part of character.
   • HP max depends on class base HP + Constitution score in DW typically. For instance, a Fighter’s HP = 10 + CON score. We should confirm each class formula (they vary in DW; e.g., Wizard is 4+Con, etc.). It might be easier to let the user input Max HP (like Roll20 does)[28], but a nice feature is auto-set max HP when class and CON are set. We could fill it initially but allow override. So consider class data: {name, baseHP, baseLoad, damageDie}. On class selection, set maxHP = baseHP + CON, maxLoad = baseLoad + STR mod.
   • Damage die comes from class but could be modified by moves (e.g., some moves might upgrade damage die one step). If a move like that is chosen, we must allow editing damage die or have it in state to adjust. Possibly simpler: store damage die in state and if a move changes it, the player manually changes it via an edit control (like a dropdown of dice).
   • XP threshold check triggers a UI state canLevelUp = (XP >= level+7). Use this to maybe enable a “Level Up” button.
   • If HP <= 0, trigger isDying = true in state which UI watches to pop Last Breath prompt.
3. Equipment Panel (Equipment List Component)
   • Data Structure: The inventory items are in one list (with an equipped flag). We can derive the equipped subset or have separate lists. Implementation options:
   • Keep a single inventory array with each item having equipped: true/false. Then Equipment panel displays inventory.filter(item => item.equipped). Inventory panel displays the opposite or all with distinction.
   • Or maintain two arrays: equippedItems and carriedItems. This may simplify separate display but duplicating items across arrays is messy; better to stick to one list with a property.
   The equipped items will typically have item.type "weapon" or "armor" or special gear that is wearable. But some items could be toggle-equipped like a ring or amulet too. Mechanically, equip mainly matters for those that provide stat effects. - UI Elements: - For each equipped item, display its name and key tags and maybe quantity if >1 (though if it’s equipped, likely quantity 1 except ammo but ammo wouldn’t be in equipped). Format example:
   [Sword] – close, 1 weight, sharp (equip icon toggled on)
   Actually in equipment panel, no need for equip icon since they’re all equipped; perhaps an “unequip” button. - If item has an associated move or detail, an info button (ℹ️) or just clicking the item row opens the Item Detail Modal. - Item Detail Modal: shows item name, full description (if any), list of tags, any special rules text. If the item grants a move or has a move, include that move text. If it’s rollable (like maybe a magic sword might have a custom attack roll?), include a roll button. - If the item has a consumable aspect (uses), show the remaining uses and perhaps allow decrementing here as well. - Modal also might have “Edit” if in an edit mode (to change fields). - Unequip button: A small button (could be an icon of a box or arrow) on each item entry to unequip. onClick -> set item.equipped = false and maybe move item in UI list. - Possibly Use button: If item is consumable or usable without being a move. For example, a healing potion: we know using it heals. We could script a specific effect (like prompt how much to heal or automatically heal a fixed amount). However, for generality, maybe the Use button just reduces the uses count and leaves it to the player to adjust HP or whatever. Simpler: have the Use button call a function that, if item.name contains known consumables, do something. But that’s too special-cased; instead, perhaps tie usage to moves (like a Healing Potion might be represented with a custom move “When you drink it, heal X HP”). Then the Use button could trigger that move’s effect (like just display text “healing for 10 HP” and the player does it). Given complexity, the Use button could simply be a quick way to decrement uses and show a note “Used 1 [item]”. - Weight and Tag display: Possibly show weight as an icon or number (like a backpack icon with number 1). Similarly, uses could be displayed as bullets or a number. Keep it concise so each item fits on one or two lines. - Ordering: Items could be sorted by type or custom order. If custom order is allowed (drag drop sort), then the underlying data structure should update an order field or reorder array accordingly. Simpler is just the array order as is. The user adding items likely appends to end, and equipping could either preserve original position or place at top of equipped list. For now, not critical. - Interactions: - Equip/unequip: If an item in this list is toggled off (unequipped), it should disappear from Equipment panel (perhaps move to Inventory panel list). We might just re-render lists based on the flag. - If using drag: dragging an item from this list to inventory list would set equipped=false. Implement via a drag event handler that updates state. - Editing an item (like changing its tags or name) typically would be done from Inventory panel, but we could allow it here via the detail modal (like an “Edit” button that turns fields into inputs). - When an item is equipped or unequipped: - Recalculate armor: If item has an armor value (we identify maybe by tags or by item.type if “armor”), update character. One approach: each armor item could have a property armorValue; sum those for equipped items to set character.armor. - Recalculate damageModifier: If weapon has a damage bonus (like the Fighter’s signature weapon could have +1 damage as a tag), we might want to incorporate that into damage rolls. Perhaps simpler: treat that as a tag and leave it to player to remember. But we can parse tags for “+X damage” or store a field. For thoroughness, maybe allow an item to have a numeric damageBonus field (Roll20 had something akin to that)[29]. Then if equipped and item.type == weapon, add to some global damage bonus state. Or just apply it when rolling damage by summing bonuses from equipped items. - Update currentWeight: equipping or unequipping doesn’t change total weight (unless we consider dropping it), because the item is still on person. If we allowed a notion of stash (not carried), that would change weight, but equip vs inventory does not change load per Roll20[24]. So no weight change on equip action unless we implement dropping. - Potentially, if an item has a tag that affects other moves (like a shield might give +1 armor, which we handle; or a tag “clumsy” might impose -1 to some actions like spellcasting – that’s a bit specific, likely handled by GM ruling, so we won’t automate that). - Use action: If uses > 0, decrement and update item. If uses becomes 0 and it’s a one-time item, maybe auto-delete or mark as expended. Possibly ask user if they want to remove it. If it’s something like Adventuring Gear (5 uses), it stays until all used then perhaps still stays but at 0? The user can remove when they feel like it. - The item detail modal if it contains a move (like our ring example) could allow rolling that move. Implementation: either represent that move in the moves list as well and have the modal call the same roll function, or embed a mini roller in modal. Possibly simplest is the modal having a button which calls a generic roll with specified formula or triggers the move if the move is listed separately. We might store a reference like item.moveId that links to a move in moves list. Or store move text in item data itself. Either approach, dev must ensure consistency (if item’s move is also in moves list, keep them synced if edited). - State dependencies: - Relies on inventory data. If the inventory list updates (items added/removed), equipment panel must update if any equipped flag changed or items were removed entirely. - Triggers updates to stats (armor, damage mod, load). - Possibly triggers changes to moves (if equipping an item grants a new move, though normally that would already be represented as a custom move the player added). But consider e.g. a magic weapon that gives a move when wielded. We might implement by instructing player to add the move when they have the item. We won’t dynamically add/remove moves on equip since that’s rare and complex. - Could interact with Session Tools if an item provides a tracker (like ring’s paradox points). We won’t automate that; the player can make a tracker manually. Or in the item’s modal, we might show a current count (like Paradox Points in ring example) which the player updates. If we wanted to support that, item data could include custom counters. But that’s beyond core, likely just instruct to use trackers.
4. Inventory Panel (Carried Items Component)
   • Data Structure: Same inventory array as above. We display all items that are not equipped (or possibly both, with equipped ones indicated). But better to separate view: Equipment panel for equipped, Inventory panel for unequipped. The inventory entries share the structure: { name, quantity, weight, tags [string], description, equipped (bool), uses (int), type ("weapon"/"armor"/"item"), value (optional cost) }.
   • UI Elements:
   • List all items (excluding those equipped, unless we decide to show with an icon that they are equipped, but that duplicates info – likely filter them out here).
   • Each item line: possibly a checkbox or icon to equip (e.g., an empty checkbox means not equipped, click it to equip – which effectively flips the flag and moves it). Or a button “Equip”. Alternatively, drag from here to Equipment list.
   • Show name (maybe allow inline editing on name for quick changes), quantity (if >1, e.g. "arrow x 10"), and weight. If quantity >1 and weight is per unit, display total weight or each unit? Possibly show “Weight: 0.1 ea” or “Weight: 1 total if trivial. To keep it easy: store weight as per unit and multiply by quantity for load calc. Show either just per item weight in tags (“1 weight” is usually per item, if multiple, player should adjust quantity appropriately).
   • If tags exist, show a preview like small badges or text. Possibly ellipsize if too long.
   • Add Item button: On clicking, open a modal form:
   o Fields: Name (text), Description (multiline), Quantity (number), Weight (number or fraction, could allow decimal if half-weight items), Tags (text, maybe comma-separated or individual tag inputs), Type (dropdown: Item/Weapon/Armor for any special handling), Uses (number, optional), Value (coins, optional).
   o Save adds a new item object to inventory state. If Type is Weapon or Armor and we have special fields like damage bonus or armor value, the form could show those too. But we can simplify: tags can cover it (e.g. tag “+1 damage” or tag “armor 2”).
   o After adding, recalc weight totals, etc. Possibly auto-sort into list.
   • Edit Item: Each item could have an edit button (pencil icon). Clicking it either transforms the line into edit fields or opens similar modal pre-filled. Save applies changes to that item in state.
   • Delete Item: A trash icon on each line to remove the item. If the item is equipped, maybe either warn “This will unequip and delete” or force them to unequip first. Safer to restrict deletion to unequipped items to avoid stat mismatch. But we can allow it and just handle it (if deleting an equipped, just remove it and update stats).
   • If the inventory is long, allow scrolling. Possibly group items by category:
   o We could list Weapons, Armor, Gear separately with headings. We have type field to filter. If so, implement three sub-lists by filter. This helps organization.
   • Weight summary: At the bottom or top of inventory panel, display something like “Total Weight: X (Load capacity Y)” as duplicate info to stats. Could also show encumbrance note here. Implementation: just compute sum of all item.weight \* item.quantity (for all items in inventory list) and show with capacity. This number should equal the Stats panel’s currentWeight for consistency[4].
   • Coins: Could include a special entry like “Coins: 50 (0.5 weight)” if we want to treat coins as item. Could hardcode an entry in UI linking to a coin count in character state. Alternatively, treat coins as just an item named “Coins” that user can edit quantity. Possibly easier to just instruct them to have a “Coins” inventory entry. If we want a field specifically: add a field in Stats or here for coins, and on update, if coin weight is considered, add coin/100 to weight. Given not explicitly asked, we can skip or do minimal (maybe in Journal to note wealth).
   • Interactions:
   • Equip: on equip (via button or drag), item.equipped = true -> triggers re-render on both panels (it disappears from inventory list, appears in equipment). Also stat updates for armor if relevant.
   • Add item: adds to state, weight recalculated (increase currentWeight). If new total weight crosses encumbrance threshold, the Stats panel encumbrance indicator updates (maybe triggers a warning icon).
   • Delete item: subtracts weight. If weight goes below threshold, update encumbrance (no longer encumbered, etc.). If item had armor or damage effect and was equipped (if we allowed deletion while equipped), update armor/damage accordingly.
   • Use/consume: If an item with uses is in inventory (like rations with 5 uses), the player could decrement uses by editing or if we provide a quick “use” button on inventory too. Possibly we treat these similarly as in equipment – a use button that reduces uses and if uses drop to 0 maybe prompt “remove item or keep at 0?”. Up to user. For persistent items like Adventuring Gear, they keep at 0 uses after all used to denote it’s expended, or remove it.
   • Validation: If an item’s weight or quantity is edited, ensure it recomputes weight totals. If an item’s type is changed to armor or weapon and it’s equipped, maybe recalc relevant stats. E.g. user edits an item to mark it as Armor type with 2 armor value and sets equipped, then armor should include it. This implies:
   o Might need additional fields when type = Armor or Weapon, like Roll20 does (Base Armor, Armor mod, Damage bonus)[30][29]. If implementing: if item.type == Armor, have item.armorValue and item.armorBonus (for shield). If item.type == Weapon, have item.damageBonus or item.damageDie (if it replaces base damage? DW rarely does that except magic weapons might say “damage die +1” which is effectively bonus).
   o For simplicity, we could parse certain tags like “Armor +1” or “Damage +1” to fill these behind scenes. Or just parse when calculating totals (scan equipped tags for “armor” or “+damage”). Maybe too much parsing – better to let user input numeric fields if needed.
   • Dependencies:
   • Inventory interacts heavily with Stats (Load, Armor, damage) as noted. So we ensure any inventory change calls functions to update those derived values.
   • Moves dependency: not many, except if an item triggers a move which we already covered via either item modals or instructions to add a custom move. The inventory system itself doesn’t automatically do moves except using the item.
   • Session Tools: dropping or losing items might be noted by the player in notes or not needed to reflect. There’s not a direct link except weight affecting a “-1 ongoing if encumbered” which the player might toggle in a global mod.
   • Class constraints: Some classes may have starting items or capacity differences. That’s initial setup (like the initial inventory could be loaded from a template when class is chosen). That’s more of a content loading issue, not interaction – out of scope, but worth noting for developer if auto-creating new character from class data (like starting gear sets).
5. Moves Panel (Moves List Component)
   • Data Structure: moves list where each move object includes:
   • name (string)
   • description or text (string, full move text including trigger and effect)
   • stat (string or null) – if the move requires a roll, store which stat mod to add (e.g. "STR", "DEX"). For moves like Defy Danger which can be multiple stats, we might either create separate entries or encode as stat=null and handle specially (perhaps when user clicks Defy Danger, prompt which stat to roll with). Simpler: treat each stat-specific variation as separate moves or prompt user each time.
   • rollFormula (if not 2d6+stat – e.g. a move might call for rolling damage or rolling + number of bonds, etc. Maybe allow formula like "2d6+CHA+bondCount". But those are rare. Possibly handle Aid/Interfere (roll+bond) by coding bondCount separately. We can keep it simple: have stat = "BOND" as a special case meaning roll + number of bonds, then interpret in roller).
   • isBasic (bool), isClass (bool), isSpecial etc. Or perhaps a category field (Basic, Class, Compendium, Custom, etc.). This aids grouping.
   • source (maybe the class or source of the move for grouping if needed).
   • Maybe levelRequired if we want to filter advanced moves until they have that level. Possibly too much; the player can decide what to add.
   • uses or recharge if a move has limited uses (rare in DW for moves, except spells which are separate). Might skip this.
   • Possibly a flag if move is currently “active” or not – but likely unnecessary.
   • UI Elements:
   • Move Group Headings: Implement as either separate lists per category or one list with headings inserted. For example, render a heading "Basic Moves" then map moves.filter(isBasic), then "Class Moves" etc. Collapsible: each heading can be a toggle that shows/hides its moves. Use an accordion UI or custom logic. Save collapsed/expanded state in local state so it persists during session.
   • Move Entry: For each move, display a row with at least the name. Optionally show the associated stat in shorthand, e.g. "(STR)" after name or an icon for the stat. The entry could have a > arrow or plus icon to expand.
   o Click on name or an expand button will reveal the full description (could slide down). The full text likely includes line breaks; style it with some indent or blockquote.
   o If the move is rollable (stat or formula given), include a Roll button on that row. Maybe a small dice icon aligned right. If the move is expanded, the roll button can either remain or be near the top of the text.
   o If the move is not inherently a roll (like some advanced moves just modify other moves, or e.g. the Thief’s flexible morality or whatnot), you can omit roll button.
   o The roll button onClick will call a roll function with the appropriate formula (2d6 + stat mod + global mod if any). That function needs access to the character state to get the stat mod (and global mod, and any situational mod).
   o After rolling, capture result: The result can be shown in a few ways:
   o In the moves list UI itself: e.g., temporarily display "Result: 7 (Partial Success)" under that move. But that might clutter.
   o Or a small overlay that fades: "Hack and Slash rolled 6 (Miss)".
   o Or, as earlier planned, a persistent Log panel. If implementing a log component, then just append the result there.
   o For now, perhaps implement a log in Session Tools or a bottom bar.
   o Potential improvement: If a roll result is shown inline, color-code and maybe summarize the outcome using the move’s text. E.g., if Hack and Slash got 10+, we know it's a success (deal damage, avoid attack). We could print that. But requires parsing move text or hardcoding outcomes – not trivial for all moves. Possibly skip, just show numerical result and success level (the player can read the move text to see what that means).
   • Add Move Button: At bottom or top of moves list, an “Add Move” button opens a modal to input a new move:
   o Fields: Name, Description (multi-line), Stat (dropdown of stats plus maybe “None” or “Custom”), Category (Basic/Class/Custom – though Basic/class usually preloaded; custom will be default).
   o If stat is set, that implies a 2d6 roll. If the move needs a weird formula, the user can either leave stat blank and just handle rolling manually or we might let them enter a custom formula (advanced feature).
   o On save, add to moves list (likely under Custom or under Class if they choose).
   o This allows adding new advanced moves when leveling, or any compendium class moves, etc. (The system could optionally have templates for known moves, but that’s beyond our design scope. It’s manual entry here).
   • Edit/Delete Move: For custom moves, we should allow editing or deletion (in case of mistakes or if a move is removed via retraining). Basic/core moves probably should not be deletable to avoid accidents, unless we allow it (some players might not want to see moves irrelevant to them – e.g., a Wizard might not care about Bend Bars Lift Gates, though technically any class can attempt any basic move, so better keep them). We can restrict deleting Basic moves by check if isBasic then maybe require an extra confirm or disallow.
   o UI: an edit icon next to move name or on expanded view. Clicking it turns the description into an editable textarea, and stat/category selectors become available. Save applies changes.
   o Delete icon maybe on expanded view or next to edit. Confirm and remove from array.
   • Scrolling: If the move list is long, allow scrolling within panel. Keep the headings sticky perhaps, so you know which section you’re in. Or just straightforward vertical scroll.
   • Interactions:
   • Rolling a Move: When user clicks roll, implement rollMove(moveId):
   o Determine base roll = 2d6 (DW default) or another formula if specified (maybe move.formula or if stat = "BOND", use number of bonds).
   o Retrieve stat mod: If move.stat is one of STR,DEX,... get character.stats[stat].mod. If a debility for that stat is active, that mod already reflects it (assuming we calculated mod with debility, or if not, subtract 1 if debility flag true).
   o Add global modifier if any (like +1 forward selected).
   o Roll 2d6 (random generation).
   o Sum = roll + mod + global.
   o Log it. Also, if result <=6, you might automatically increment XP (character.XP++ and update state) because fail = XP in DW. Or at least set a flag for user to confirm XP. We can directly do it to reduce forgetting, since single-player likely appreciates it. Roll20 doesn’t auto-add XP, but it has a GM. Here we can be a helper.
   o If XP changed, check if threshold reached and maybe flash the XP or show level-up prompt.
   o Additionally, if move is Aid/Interfere (roll + bond), we would need to know bond count. Possibly, when adding a move, if stat is set to “BOND”, we interpret that as use number of bonds. The player could input the number in a prompt or we fetch from how many bonds they have listed (which if we had bond entries count, we could use that). If we store bonds as array, bond count = array.length. Could use that. For now, we can simply prompt: “How many bonds? (Enter number)” when rolling Aid.
   o After roll, maybe show a quick outcome categorization: check if >=10, 7-9, or <=6, and attach label "Strong hit / Weak hit / Miss" (or just “Strong/Partial/Miss”). This is easy to do and gives immediate context. The actual consequences text the player reads from the description anyway.
   • Non-Roll Moves: If a move has no stat (e.g., a passive move), then no roll button. Clicking it just expands info. Some moves require choices or spending hold etc., but handling that is beyond automation – the player will use trackers or notes for hold. Our UI just provides the info.
   • Spellcasting: For spells, if integrated here, each spell could be a move entry with no roll but maybe a “Cast” button that essentially triggers the Cast a Spell move (which is actually separate). Possibly not linking directly. The player would likely just use the Cast a Spell move from basic moves which covers any spell.
   o Managing spells might involve tracking prepared/unprepared. A separate spells subsection might list spells with checkboxes (prepared). Or simply treat spells as custom moves that are only available if prepared (maybe mark prepared ones differently).
   o Could integrate with trackers (e.g., “Spell slots remaining” as a tracker) or just rely on notes.
   o Given complexity, we might treat spells outside of core moves: have a Spells panel or incorporate in Inventory as special items. But since not explicitly required, we note it's possible but focus on main moves.
   • Search: If implementing a search bar, onChange filter moves list (match in name or text). Ensure that doesn’t break the layout; just show filtered results maybe under a “Search results” heading or highlight matching ones. This is a nice-to-have for devs to implement if time.
   • Dependencies:
   • Stats: moves rely on stat mods from Stats panel. So if a stat changes (like mod due to leveling or debility), ensure that the next roll uses updated mod. If using a direct read from state each time, it’s fine. If we cached anything, update it.
   • Inventory: typically none, except if an item grants a move and the user has added it, or if bond count is needed for Aid move (bonds possibly stored in journal or some structure).
   • Session Tools: if a move result gives hold, the user uses trackers. No direct link except maybe the suggestion to auto-create trackers for certain moves (not doing automatically but perhaps mention).
   • End of Session & Level Up: those are moves too. The End of Session move we turned into a guided workflow – in code, that could be triggered when user clicks an End Session button, which then calls functions to do XP prompts. The Level Up move similarly triggered by XP threshold and user action. We might not treat those as normal moves with roll, but as special functions because they involve UI flows not just text. Alternatively, we could store "End of Session" in moves and when user clicks it, just display text instructing them. But better to implement as interactive form for user experience.
   • If any move or advanced feature interacts (like some moves modify other moves’ outcomes), we assume the player will interpret that; we don’t need to encode those relationships.
6. Session Tools Panel (Tools Component)
   This panel likely contains multiple sub-tools. Implementation could be each tool as a sub-component, all stacked in a scrollable drawer.
   • Dice Roller Subcomponent:
   • Could be as simple as two controls: one to select dice formula, one button to roll.
   • For ease: a text input where user can type something like “2d6+1” or “1d8” or “3d6+2d4+3” etc., and a Roll button that parses and rolls it. But parsing expressions can be complex. Alternatively, a dropdown for dice type (d4,d6,d8,d10,d12,d20,d100) and an input for number of dice and mod.
   • Perhaps have quick preset buttons:
   o “Roll 2d6” (most common)
   o “Roll d4, d6, d8, d10, d12” (for damage or random).
   o If clicked, it rolls that immediately, or fills the form field with that for further editing.
   • Implementing roll: generate random numbers, sum, output to log. If mod included, add it. If multiple dice, you could list individual results or just sum depending on clarity.
   • The roller might also be used by other parts (the move roller basically does 2d6 + mod, which is similar). We could unify roller logic in a utility function.
   • UI also maybe show the result in a big font for a second or two in the dice area, then also log it.
   • Possibly allow toggling whether to add to last rolled result (like maybe roll damage twice and take higher, but that's too niche to implement specifically).
   • Key: make sure roller is always accessible – since we have it in a drawer, user must open drawer to use it, unless we put a mini roller somewhere persistent (maybe not needed, drawer opening is just one click).
   • Notes Subcomponent:
   • Could be one multi-line text area (automatically saved on changes, maybe with placeholder “Session notes…”).
   • Or a list of short notes entries: maybe have an input box to quickly add a one-liner that gets listed with timestamp. But the prompt specifically says note keeper, likely implying possibly more than one note or at least the ability to keep multiple pieces of info.
   • A compromise: have a multi-line area but also an “Add Note” button that timestamps and starts a new block, effectively chunking notes by time.
   • For ease of dev: just provide a big text area that is persistent. The user can write whatever and separate by lines or headings themselves. That might be enough.
   • Provide perhaps formatting (maybe not needed).
   • Possibly a button to “send to journal” or mark certain lines to later move to the permanent journal.
   • But not required. Simpler: raw notes which user can later manually incorporate into journal.
   • Trackers Subcomponent:
   • A list of trackers, each with:
   o A title (short text)
   o A current value (number)
   o Maybe a max value (optional).
   o Buttons + and -.
   o Possibly an edit button to rename or change the current/max directly.
   o Add Tracker: opens small prompt to enter title, starting value and optional max.
   • Represent trackers in state as array of { title, current, max? }.
   • If value hits some bound (like 0 or equals max), maybe highlight. E.g., if a tracker called “Torch light” reaches 0, turn the text red. We can let the user remove it when done or leave it.
   • Removing tracker: a delete button (X) on each tracker.
   • The + button: increment current by 1 (not beyond max if max set, or allow and just note it’s over).
   • The - button: decrement (not below 0 ideally).
   • Potential fancy: if tracker title contains “hold” or “Hold”, maybe automatically remove when hits 0 (since hold often is one-time). But that’s assumption; better not to enforce.
   • Timer/Clock Subcomponent:
   • Could implement a simple timer that counts up from 0:00. Press a “Start” button to begin, which changes to “Pause” and “Reset”. This tracks real time. Might not be heavily used but easy with JS setInterval. Display minutes:seconds or hours if long.
   • Or implement a countdown: user inputs minutes or a specific target time and hit Start. The UI then counts down and when hits 0, maybe flashes or rings (if we include sound).
   • Since not a core mechanic, a minimal approach: one stopwatch. That suffices for “session duration” or any general timing.
   • Bookmarks: Could integrate with timer if one exists (like mark at 30min). But easier: a Bookmark just logs a timestamp and comment in notes or log.
   • Implement Bookmark: a button “Add Bookmark” opens a small input for a label, or if none given, just uses current time (either real time or session timer time). Then it appends something in the notes or log like “--- Bookmark: label (hh:mm) ---”. Or push a bookmark object in an array that the notes section or journal can reference. Probably easiest: insert a line in notes text area with a distinct format (like prefix with \*\*\* or something).
   • Log Panel:
   • If we treat the log of rolls as part of session tools, it could appear at the bottom of the drawer or even at bottom of screen. It might not require user input, just display.
   • Implementation: store an array of log entries, each could contain text (and maybe type, like “move” or “dice” or “info”).
   • Each time a roll or significant event happens, push to log.
   • Display it as a scrollable area with the latest at bottom. Use monospace or distinct style for dice results.
   • Possibly include timestamps if needed (or not necessary).
   • If user adds a bookmark or if end-of-session XP triggers, log those as well (“+1 XP (End of session question)” etc., to have a record).
   • Ensure the log persists through session but probably reset or archived when session ends (maybe a new log each session or it just keeps growing; user can clear it if desired).
   • Inter-component Interactions:
   • If a move roll triggers adding XP, the Session Tools could log “Gained 1 XP” or perhaps the XP addition itself is enough feedback. But logging it is nice for record.
   • If implementing the session timer, when End of Session happens, we might stop it and include the total time in the session summary (e.g., in an end-of-session popup say “Session lasted 2h 14m” just as trivia).
   • The notes and journal interplay: maybe allow copying notes to journal at end. Could implement a function that on end session, either auto-copies the notes content into a new journal entry (then clears notes) or at least suggests the user to do so. But we can leave that manual to avoid unexpected overwrites.
   • State Persistence: The content of notes and trackers should be saved with the character, not just ephemeral, because a player might take a break mid-session or want to carry some notes forward. However, some trackers (like hold) are probably only meaningful in the current scene – but still, better to save everything and let the user clear what’s obsolete. So ensure notes text and trackers array are part of character save.
   • No Multiplayer/GM integration: Since single-player, we don’t need any networking or sync. Everything is local. The dice results don’t need to be broadcast, etc., which simplifies dev (no need for cryptographically secure dice or such unless user cares).
   • Extensibility: The tools panel is mostly generic, so adding new kinds of trackers or counters is easy (just new entries). Could in future integrate an oracle or GM emulator for solo play (some solo players use random prompts), but that’s beyond current scope.

   • id, title (string), date (timestamp or date string).
   • content (string, potentially multi-line with formatting).
   • Possibly tags or category if we wanted to classify (NPC, Quest, etc.), but we can start simple without.
   • UI Elements:
   • A list or navigation of entries on the side, and a viewing/editing area on the right. However, given the main layout, maybe the Journal panel itself shows either a list of entry titles which you can click to open the content. Alternatively, show the most recent entry by default and list others as collapsible older logs.
   • Perhaps a two-column layout within Journal panel: left subcolumn with a scrollable list of titles (with dates), right subcolumn showing selected entry content. This is typical of note-taking apps. On smaller view, could just show list and clicking one opens it replacing list.
   • Add Entry button: prompts for title (maybe default to current date as title if not given) and opens a blank area to type content. Once saved, adds to list.
   • Edit Entry: if viewing an entry, an edit button toggles the content area to editable (textarea or a rich text editor if we allow formatting). Save writes back to entry.
   • Delete Entry: a delete button on an entry (maybe in list with right-click or a trash icon) to remove if needed.
   • Formatting: We can allow Markdown or basic formatting (bold, italic, bullet points). That can be done with a rich text editor control or just assume plain text and encourage Markdown syntax with preview. Simpler approach: a plain textarea but we allow Markdown in content and render it when not editing (the developer can integrate a Markdown parser for display).

   • Extensibility:
   • Journal content can hold any homebrew lore, maps (if we allow image attach in rich text), etc. The design doesn’t restrict that.

8. State & Rule Enforcement
   The system should respect Dungeon World mechanics: - Stat Mods: Use correct mapping of scores to mods[27]. Typical DW uses same as D&D: 3-5: -3, 6-8: -1, 9-12: 0, 13-15: +1, 16-17: +2, 18: +3. Developer to ensure calculation or table reflects this. Or allow manual entry if easier but auto-calculation is nicer. - Debilities: Each debility is a -1 to the associated stat mod[3]. No more than -1 per stat (they don’t stack beyond one per stat). Implement as described (checkbox subtracting 1 from mod). - Moves Rolls: Always 2d6 + relevant mod (with perhaps bond count or other special mod in a few moves). No advantage/disadvantage mechanics needed (DW doesn’t have that). - Damage Rolls: Typically 1 die as per class or monster. The player’s damage die is fixed, possibly with bonus. We should allow adding damage bonus (like Merciless or weapon tag) to damage rolls. Could implement a damage roll function that uses base die plus sum of any bonuses from equipped items or moves (we can maintain e.g. damageBonus in state default 0 and increase it when a relevant move is acquired or toggle on a global mod if they choose). - Armor Calculation: Sum of equipped armor pieces’ values[5] plus any moves (e.g. a move might give +1 armor when some condition; we could let the player manually adjust armor or use global mods if short-term, but one could also treat that move as giving a passive stat we incorporate via manual entry). - Load & Encumbrance: Already covered; just ensure the logic for encumbrance is correct (<=Load: no penalty, <=Load+2: -1 ongoing (we might not auto-apply but could warn), >Load+2: cannot even move normally (we can strongly warn the player). Possibly highlight encumbrance state to remind them to apply the -1 forward in fiction). - XP and Level Up: The threshold formula current level + 7[7]. After leveling, subtract threshold from XP or reset to 0 and keep remainder (DW doesn’t explicitly say to keep remainder, but often you do keep overflow XP). We should handle that: e.g. if XP was 10 and needed 10, now XP=0 and level++ (no overflow). If XP was 12 needing 10, after level up XP could be 2 (overflow). We can implement that easily when leveling up. - End of Session XP: Provide interface for those 3 questions[26] and bonds/alignment. The system doesn’t inherently know if answers are yes or no (that’s up to player), so just let them input and then add XP accordingly. Bonds resolution might require listing bonds to choose from – if bonds stored as array of strings, show each with a checkbox “resolved?”. If one is resolved, perhaps prompt the user to remove or rewrite it (but rewriting bond is creative, we can’t auto-suggest content; just let them handle in notes). - Hold & Ongoing Effects: We don’t automate hold usage beyond trackers. It's the player’s job to spend them, we just provide the means to track it. Ongoing bonuses/penalties like -1 ongoing from encumbrance or spells – the player can toggle the global mod or just account manually. - Safety Checks: Prevent impossible values (HP current not above max, or below 0 beyond dying state, stats not below 0 or above 18 normally, etc., unless someone really wants weird values). Soft-limit or at least handle extremes. For instance, if a stat is increased above 18 by level up, cap at 18 (DW rule: stats max at 18). - Extensibility for Homebrew: Allow adding new stats or fields if needed? Usually not necessary for DW, but maybe “Luck” or “Mana” if someone hacks it. They could use trackers for new resources. Or if a user’s homebrew adds a new stat, that’s big – likely out of scope, they'd need code changes. But generic design is flexible enough to at least let them track custom stuff in notes/trackers. - Content Extensibility: The system can be populated with default moves for a chosen class for convenience (like how Roll20 does via compendium)[32][33], but if not, the player can add everything manually. We support manual addition of moves, items, etc., which inherently supports any homebrew content (they just type in their custom moves or items). DungeonPaper advertises class and race creation[16] – in our system, that equates to letting the user define new moves, starting stats, etc., which we do. - No Unnecessary Aesthetics: The UI will be functional: minimal graphics, perhaps just icons for clarity (stats icons, etc.), ensuring it runs smoothly even on modest systems (since it’s desktop). The focus is on structure and quick interactions, not fancy animations (aside from small feedback ones) or heavy artwork. This also makes it easier to extend, as new panels or fields can be added without reworking a visual theme.
   In conclusion, this design provides a comprehensive, modular control panel for a Dungeon World player. It covers all crucial character information (stats, moves, gear) in dedicated panels for clarity, and offers a suite of session tools to replicate the tabletop experience (dice, notes, trackers) digitally. Each component is designed with Dungeon World’s rules in mind, ensuring, for instance, that equipping armor adjusts your Armor stat[5], carrying too much weight warns of encumbrance[9], and missing a roll reminds you to mark XP. The interface facilitates rapid context switching – a player can go from checking a move, to rolling dice, to writing a note in a heartbeat – which is vital for keeping pace with the narrative. Moreover, it’s built to handle the campaign’s growth: new moves from leveling, new loot, evolving notes, all can be added easily without redesign. By focusing on usability (few clicks, informative feedback) and clarity (logical layout, visible important data), this control panel will help a solo Dungeon World player manage their adventure effortlessly, much like a well-organized paper character sheet combined with the conveniences of modern app technology. All these design choices aim to let the game’s story take center stage, with the mechanics smoothly supported in the background, true to the Dungeon World spirit.
